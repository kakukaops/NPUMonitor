# 异构加速器监控目录规划

日期：2026-11-12。状态：已执行设备归类、模型服务和公共集成提取；公共Web/编排及NPU业务实现按阶段继续。用于后续 NVIDIA GPU 和 Huawei Ascend NPU 开发。

## 1. 设计决策

按“公共平台能力 + 厂商设备包”划分，设备包内部再区分规则和机器学习。顶层项目定位为异构加速器监控，GPU、NPU各有独立入口、指标契约、实现、部署配置和验收证据。

当前已实现的是 NVIDIA/DCGM GPU 能力，Huawei NPU 为待开发范围。Ascend 是本次 Huawei NPU 的设备分类；以后其他厂商GPU、其他产品线NPU增设同级目录，不将所有GPU归入NVIDIA、不将所有NPU归入Huawei。

## 2. 目标结构

下列为目标目录；标为“待提取”的部分不能据此认为已经通用化。无实现的目录不预先创建空壳。

```text
modules/
├── platform/                         # 与厂商无关的运行能力（待提取）
│   ├── contracts/                    # 设备身份、观测、能力声明、结果协议
│   ├── integrations/
│   │   ├── prometheus/               # 查询、鉴权、超时；不内置DCGM查询
│   │   └── nightingale/              # 规则同步、事件/通知适配
│   └── ml-monitoring/                # 通用任务、模型引用、评分编排、Web/API
│       ├── backend/
│       ├── frontend/
│       ├── tests/
│       └── docs/
├── model-services/                   # 模型服务与设备监控独立
│   ├── contracts/                    # 训练/部署/预测协议，唯一事实源
│   ├── adapters/                     # 参考HTTP、公司平台适配器
│   ├── reference-platform/           # 可选的独立训练/部署/推理服务
│   └── runtime/                      # 可复用数值算法，禁止内置DCGM字段
├── devices/
│   ├── nvidia-gpu/
│   │   ├── README.md
│   │   ├── common/                   # NVIDIA指标、硬件范围、来源、契约
│   │   ├── adapters/                 # DCGM字段与设备身份映射
│   │   ├── rules/                    # 原规则模块，保留内部子目录
│   │   └── ml/                       # GPU检测场景、特征、配置、测试、证据
│   └── huawei-npu/
│       ├── README.md
│       ├── common/                   # Ascend指标、型号、固件和来源
│       ├── adapters/                 # 实际采集器、字段、设备身份映射
│       ├── rules/                    # NPU规则、处置、测试、验收
│       └── ml/                       # NPU场景、特征、配置、测试、证据
└── layout-migration.json             # 历史路径追溯

deploy/
├── shared/                           # 夜莺、Prometheus等基础组件
├── nvidia-gpu/                       # GPU采集和实验组合
├── huawei-npu/                       # NPU采集和实验组合
└── model-platform/                   # 可选参考模型服务

docs/                                # 跨设备架构、接入规范、迁移规划
scripts/                             # 全仓检查、构建及历史命令包装
.local/                              # 私有凭据与本地数据，不提交
```

`devices/*/rules/` 和 `devices/*/ml/` 统一按需使用 `docs/`、`config/`、`src/`、`tests/`、`scripts/`、`evidence/`。已有规则模块内部目录在第一阶段保持，避免把设备归类和内部代码重构混在一次迁移中。

## 3. 现有目录如何归属

| 迁移前路径 | 目标归属 | 处理原则 |
|---|---|---|
| `modules/gpu-monitoring-common/` | `modules/devices/nvidia-gpu/common/` | 全部先归NVIDIA；DCGM字段、H100资料不能进入平台公共层 |
| `modules/gpu-monitoring-rules/` | `modules/devices/nvidia-gpu/rules/` | 保留内部实现和冻结载荷；共用资产相对链接重新定位 |
| `modules/gpu-monitoring-ml/model_platform/` | `modules/model-services/reference-platform/` | 独立服务、独立存储，不依赖GPU监控主进程 |
| `modules/gpu-monitoring-ml/backend/gpu_ml/model_backends/` | `modules/model-services/contracts/`、`adapters/`及平台编排层 | 按职责拆分；training协调器属监控编排，不能整体挪成模型SDK |
| `modules/gpu-monitoring-ml/model_runtime/` | `modules/model-services/runtime/`及NVIDIA ML包 | 通用算法进入runtime；dcgm_scenarios及GPU特征留设备包 |
| `modules/gpu-monitoring-ml/backend/`、`frontend/` | `modules/platform/ml-monitoring/`及NVIDIA ML包 | 去掉硬编码场景后提取平台；GPU场景、仿真、指标查询及页面专属配置留设备包 |
| `modules/gpu-monitoring-ml/docs/`、测试、证据 | 按主题归平台、模型服务或NVIDIA ML包 | 历史GPU验收仍标GPU，不转成NPU验收 |
| 根 `deploy/` 和ML模块 `deploy/` | 根 `deploy/shared/`、设备和模型服务子目录 | 单一编排入口引用各组件；保留现有卷与项目身份 |

迁移前模型runtime依赖 `gpu_ml.settings`、`evaluation`。本轮已用通用注册表、显式schema和设备扩展替代这项依赖，评估代码归通用runtime；参考平台为GPU部署显式安装NVIDIA扩展，并保留历史制品兼容模块。旧pickle模块路径需要兼容加载或显式迁移，不能随意改包名。

## 4. 共享边界与依赖方向

设备包依赖公共契约和集成接口；公共平台通过注册表加载设备包，不在公共代码里写分散的厂商判断。参考模型服务依赖模型契约、通用算法及请求中的显式特征定义，不访问夜莺、不自行读取Prometheus。公司平台通过适配器替代参考服务。

规则、ML共用同一设备指标契约，各自保留判据、场景、执行和验收。NPU不复制GPU后端和前端；目标界面将提供设备类型、厂商及型号筛选，按设备包显示可用指标、规则和ML场景。设备包注册加载在接口稳定后实现，当前不承诺动态安装插件。

NVIDIA和Huawei的温度、利用率等名称相近不代表语义一致。原始指标名保留，规范指标需逐项声明单位、类型、采样粒度、有效值、计数器复位、标签及支持设备。只有确实等价的字段才映射到相同语义；不支持、缺失、非法、陈旧分别表示，不能用0补齐。

设备身份至少表达厂商、设备类型、集群、节点、稳定设备标识，并允许物理设备、逻辑分区、芯片等层级及父子关系。DCGM GPU UUID不得强制用作Huawei身份；NPU实际稳定标识须在采集器核实后确定。查询、事件去重、模型引用、缓存和存储键均需包含设备命名空间，不能只按卡序号区分。

模型按设备类型、型号/能力、场景、特征schema和版本绑定。共享算法和模型平台不表示GPU权重可直接用于NPU；数据契约不匹配时拒绝评分，需独立训练和验证。

共享的是连接、调度和界面框架，不在此次目录规划中新增通用规则执行引擎，也不把现有NVIDIA规则阈值复制成NPU阈值。

## 5. 分阶段实施

### 阶段一：现有资产按设备归类

迁移GPU三个模块到 `devices/nvidia-gpu/`；为NPU编写接入需求和来源台账。同步修复源码路径、Docker构建上下文、Compose挂载、脚本、生成器、Markdown、10个公共视图及布局检查器；扩展迁移登记。保持历史入口薄包装和旧Python模型加载路径，避免建立第二份实体文件。

冻结规则、输入契约和验收载荷保留摘要。历史路径可追溯，不改写历史验收事实。保持现有端口、Compose项目名、卷名、数据库、规则ID、通知目标和凭据位置；不重新初始化、不全量重导入。代码迁移需要重建时保留数据并验证挂载。

### 阶段二：提取已存在的公共能力

先迁出模型服务及协议，再提取Prometheus/夜莺接口与ML编排界面，最后将GPU场景注册成设备包。通过依赖检查保证平台不导入NVIDIA场景，模型服务不导入监控引擎；使用现有GPU行为测试验证兼容。每一步单独验收，不进行一次性大改名。

### 阶段三：接入Huawei Ascend NPU

先确认设备型号、物理/虚拟形态、固件/CANN及实际采集器版本和样本；建立NPU输入契约、指标台账和支持能力矩阵。完成真实采集到Prometheus的连通及身份验证后，分别开发NPU规则、ML场景、模拟和真实设备验收。依赖作业等当前没有的数据的场景保持未启用。此阶段再确定具体采集组件和规则依据，不预设GPU指标在NPU上存在。

## 6. 验收与当前状态

迁移验收包括路径/链接/摘要/Compose检查、规则测试、ML测试、历史模型加载、独立模型平台调用、备份恢复和页面设备隔离。NPU测试独立记账，GPU模拟通过不代表NPU通过。增加设备包隔离检查：NPU不能引用DCGM配置，公共平台不能硬编码GPU字段，跨设备模型schema不匹配必须拒绝。

实际落地位置、已提取能力、兼容边界和验证结果见[迁移与验收](异构加速器目录迁移与验收.md)。GPU页面和含DCGM的编排仍由NVIDIA模块负责；目标树中的完整公共Web/API与NPU能力不因目录归类自动完成。
