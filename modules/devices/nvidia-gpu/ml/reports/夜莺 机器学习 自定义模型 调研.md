# 在夜莺上接入规则与自定义机器学习

**可以在现有夜莺基础上实现“规则 + 机器学习”，但需要区分官方检测插件与自有模型接入。** 官方有商业“夜莺智能检测插件”，可以集成开源夜莺；当前核查的开源 v9.3.0 评估路径并不是通用模型训练、上传和推理平台。公开资料尚未证实商业插件允许上传自训练权重或注册自定义算法。对你已经完成的 demo，建议继续让模型独立运行，将检测结果写入现有 Prometheus，再由夜莺普通告警规则消费。这样可以自主替换模型，同时复用夜莺的告警管理能力。

| 路线 | 已核实能力 | 自定义模型边界 |
|---|---|---|
| 官方智能检测插件 | 学习时序趋势、反馈训练效果，与开源夜莺集成 | 自带权重、算法 SDK、第三方推理协议未获公开证实 |
| 开源夜莺 + 外部模型 + Prometheus | 普通 PromQL 规则查询模型输出并生成事件 | 模型完全自主管理，推荐当前采用 |
| 外部模型直接推送检测结果 | v9.3.0 存在外部结果接口 | 需要规则、身份、恢复与重试适配，不是模型执行 SDK |

**官方已有相近能力，但不是开源版附带完整模型平台。** 当前插件页明确介绍时序趋势预测、训练效果反馈及与开源夜莺集成；专业版页面也说明可单独购买智能告警插件，因此不必为了智能检测先整体迁移专业版。插件是否兼容当前部署的 9.3.0，以及具体算法、私有化资源需求，仍需实际发行包或厂商文档确认。([智能检测插件](https://flashcat.cloud/product/flashcat-aiops-alert/)、[专业版说明](https://flashcat.cloud/product/flashcat-pro/))

“支持调用检测 API”与“支持装入自己的模型”也不同。官方文章说明外部系统可以创建检测任务、查询结果，这证明可以调用厂商检测服务；没有由此证明能上传 sklearn、PyTorch、ONNX 模型。官网“模型自选”所在语境是 AI Agent、大语言模型与事件摘要，也不能当作时序异常检测 SDK 的证据。([官方检测介绍](https://flashcat.cloud/blog/n9e-support-anomaly-detection/)、[当前官网](https://n9e.io/zh/))

**源码支持接收检测结果，尚未核实原生自定义模型加载能力。** 在 v9.3.0 中，`GetPromAnomalyPoint` 执行 PromQL，再把结果转换成告警异常点；名称中的 `Anomaly` 不代表内部运行机器学习。本次核查的评估和数据源路径未找到模型上传、训练注册或通用 HTTP 推理 SDK；这是一项有范围的源码核查结论，不是对所有版本、商业代码的绝对判断。([v9.3.0 评估源码](https://github.com/ccfos/nightingale/blob/v9.3.0/alert/eval/eval.go))

v9.3.0 的 `POST /v1/n9e/make-event` 可接收外部异常或恢复结果，但依赖已存在的外部规则处理器，并受 `APIForService` 配置控制；默认配置关闭。它要求适配规则身份、标签、触发及显式恢复。`/event-persist` 主要负责持久化，不能等同完整告警生命周期。当前无需为了接入模型启用这些接口。([路由](https://github.com/ccfos/nightingale/blob/v9.3.0/alert/router/router.go)、[处理逻辑](https://github.com/ccfos/nightingale/blob/v9.3.0/alert/router/router_event.go)、[默认配置](https://github.com/ccfos/nightingale/blob/v9.3.0/etc/config.toml))

**推荐架构保留夜莺的告警职责。** 原始指标继续进入 Prometheus，外部模型 Worker 查询、推理并导出分数、阈值、异常状态、基线和推理新鲜度；夜莺定期查询这些指标，统一处理持续时长、事件、屏蔽及通知。硬阈值告警独立保留，机器学习规则并行补充；只在明确的软阈值场景使用“规则条件 AND 模型异常”，避免模型失效阻断关键故障告警。该方案基于夜莺原生 PromQL 告警机制和 Prometheus 标签匹配能力，不需要修改夜莺源码。([夜莺告警流程](https://flashcat.cloud/docs/content/flashcat-monitor/nightingale-v9/usecase/alerting/)、[PromQL 运算符](https://prometheus.io/docs/prometheus/latest/querying/operators/))

当前 demo 的状态可以直接通过夜莺已有 Prometheus 数据源查询：

```promql
(ml_demo_alert_active{job="ml-anomaly-demo"} == 1)
and on(job,instance,service)
(time() - ml_demo_last_success_timestamp_seconds{job="ml-anomaly-demo"} < 10)
```

十秒新鲜度门限仅适用于当前两秒采集的 demo。模型已有 3/5 持续性判断，夜莺再配置持续时长会叠加延迟。还必须独立监控模型服务 down、推理过期和输入缺失；过滤旧结果不代表业务恢复，需专门验收无数据时的告警与恢复语义。

现有 demo 已完成模型输出进入同一个 Prometheus，并通过四类注入及恢复测试；**尚未创建夜莺 ML 告警规则和原生仪表盘**。下一步应导出预测基线和上下界指标，在夜莺创建业务规则、ML 规则与模型健康规则，再验证触发、恢复、通知和进程中断。训练、版本管理、灰度及回滚仍由模型服务负责。([demo 说明](/home/mqq/github/zj/NPUMonitor/modules/devices/nvidia-gpu/ml/demo/README.md)、[验收记录](/home/mqq/github/zj/NPUMonitor/modules/devices/nvidia-gpu/ml/evidence/anomaly/acceptance.json))

如果希望减少算法开发工作，可以试用官方插件；如果重点是自主训练和替换模型，当前指标接入路线更符合需求。购买前应要求厂商明确提供自定义算法或权重接入契约，不能仅凭“智能告警”或“算法优化支持”作出判断。本次只完成调研，没有变更夜莺规则或启用外部事件接口。
