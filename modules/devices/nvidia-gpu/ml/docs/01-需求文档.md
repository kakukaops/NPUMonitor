# GPU 机器学习监控模块需求文档

> 实现进展（2026-11-11）：GPU专项独立服务、Web、训练/模型管理及夜莺闭环已形成可运行预览版。本文保留原设计/计划，实际实现与未准入范围见[实现与验收报告](06-实现与验收报告.md)，操作见[运行指南](05-运行与接入指南.md)。真实H100、生产规模和浏览器视觉验收不因代码完成自动通过。

版本：0.1  
日期：2026-11-11  
状态：设计基线，待真实数据适配及实施验收  
关联：[模块入口](../README.md)、[技术方案](02-技术方案.md)、[项目计划](03-项目计划.md)

## 1. 需求理解

### 1.1 最终目标

在开源夜莺基础上，整合此前 GPU 指标研究和规则监控能力，增加基于机器学习的异常检测，形成“规则检测 + ML 检测 + 输入质量 + 平台自身健康”的 GPU 监控体系。

用户通过独立系统查看同一批 GPU 的指标、规则事件、模型异常、覆盖和数据质量，完成模型选择、历史训练、回放和发布。业务告警对接夜莺，复用现有事件与通知能力。

“完善”指对已定义范围建立可追溯的检测和覆盖，不承诺所有硬件故障、训练失败和性能问题都能从现有时序指标推断。

### 1.2 已确认决策

| 项目 | 本期决策 |
|---|---|
| 产品形态 | 独立 Web、独立管理与计算服务 |
| 数据 | 使用夜莺当前配置的 Prometheus 中已有 GPU 指标；默认只读查询 |
| 规则基础 | 复用现有 GPU 指标、规则、诊断视图和生命周期研究，不重写一套硬件规则 |
| 告警底座 | 夜莺；ML 检测结果经适配生成夜莺原生事件 |
| 硬件首版 | 沿用 H100 物理 GPU 训练、无虚拟化范围；实际形态和 MIG 模式仍需核实，MIG 实例级不纳入首版 |
| 模型能力 | 可选内置算法训练、复用适配的已发布模型、训练新版本；自定义模型以统一适配协议分阶段实现 |
| 页面统一 | 独立页面先实现 GPU 视角统一展示；夜莺内插件化和前端改造仅为备选 |
| 目录 | 新增 `modules/devices/nvidia-gpu/ml/`，与现有 `modules/devices/nvidia-gpu/rules/monitoring/`、`modules/devices/nvidia-gpu/rules/rules/` 分离 |

“夜莺数据”是其已接入的时序数据源，不是从夜莺页面抓曲线，也不是用夜莺事件库替代原始时序。

### 1.3 本轮交付边界

立项时先建立模块目录与本需求/方案/计划。后续已实现GPU专项独立服务与Web，并在模拟GPU、实际Prometheus和夜莺链路中验证；当前实现和仍未准入范围以06号报告为准，不把实验通知等同生产通知。

## 2. 现有基础与复用边界

### 2.1 已有资产

| 资产 | 已有证据与边界 |
|---|---|
| GPU 指标总台账 | 92 项候选输入，包含设备、遥测、质量和外部上下文；并非 92 项均已采集 |
| H100 综合候选库 | 42 项输入、45 条规则、25 个诊断视图，已有模拟验收 |
| 综合规则验收 | 56 个实时场景；离线 351 用例、830 断言、27 单元测试，真实 H100 为 `not_run` |
| 持久恢复实验 | 已验证缺数保持、有效证据解除的实验适配；生产门禁未完成 |
| 通用 ML Demo | Prometheus 实际链路、Ridge 和森林组合、独立 Web、四类注入验收；输入为通用模拟服务指标 |

证据以现有[指标台账](../../common/monitoring/catalog/metric-inventory.yaml)、[综合验收](../../rules/monitoring/h100-training/acceptance-results.yaml)、[恢复策略](../../rules/docs/09-硬件告警保持与解除策略.md)和[ML原型说明](../demo/README.md)为准。本文不重新宣称上述测试在本轮运行过。

### 2.2 责任边界

- 原规则库继续维护硬件判据、单位、字段版本、覆盖和硬件恢复语义；新模块只引用其稳定 ID 与版本。
- 模块可以显示规则事件、关联模型异常，但不复制管理所有既有规则，更不覆盖本地修改和启停决定。
- ML 识别统计或条件偏离，不产生“硬件已修复”“应 RMA”“训练已失败”等无证据结论。
- 规则、ML、质量和平台状态分别记录，不压缩成一个会掩盖未知状态的健康分数。

## 3. 用户与场景

### 3.1 用户

- 值班运维：查看 GPU 状态、原始证据、规则事件与模型异常，定位需要关注的实体。
- GPU 平台维护者：核实采集、字段和拓扑能力，管理任务、数据质量和告警绑定。
- 模型维护者：选择训练范围、回放、校准、发布、回滚和分析反馈。
- 管理员：管理数据源凭据、访问权限和资源预算；普通用户不得获得后台管理凭据。

### 3.2 首期检测场景

| ID | 场景 | 用户价值 | 必要限制 |
|---|---|---|---|
| GPU-ML-01 | 在可比负载下 GPU/HBM 温度持续偏高或热余量下降 | 提前发现相对基线变化 | 有效温度与足够训练数据；负载输入可选但影响结论等级 |
| GPU-ML-02 | 功耗、利用率、时钟的联合关系偏离 | 识别未触及硬阈值的行为变化 | 高利用率、高功耗本身正常；缺输入时模型不可用 |
| GPU-ML-03 | 利用率/显存活动模式突变或持续低于自身基线 | 提供负载行为变化线索 | 无作业/阶段上下文时不能称为训练卡死或效率故障 |
| GPU-ML-04 | 可比同组 GPU 的持续偏离 | 识别群体中的异常实体 | 必须有可比组、足够成员和有效重叠数据；没有时显示不可评估 |
| GPU-ML-05 | 互联错误活动或热限制时长的异常趋势 | 补充长期变化观察 | 后续阶段；稀疏计数优先统计与规则，不强行用森林 |

ECC、SRAM、行重映射失败、XID/SXid、预期链路掉线和 Fabric 状态继续优先使用已有规则；它们可以作为解释和排除窗口，不是必须经过 ML 同意的信号。

## 4. 功能需求

| 编号 | 需求 | 验收要求 |
|---|---|---|
| FR-01 | 数据源接入 | 接入已有 Prometheus，检查连接、认证引用、采样和保留范围；查询原始源不写配置或数据 |
| FR-02 | GPU 身份与发现 | 以 cluster_id + GPU UUID 为主键，GPU 序号作展示；设备更换不继承旧状态 |
| FR-03 | 指标能力映射 | 从已有台账绑定实际名称、单位和值域；明确可用、缺失、未核实、不适用与不支持 |
| FR-04 | GPU 数据质量 | 逐字段处理 sentinel、NaN/Inf、重复、陈旧、缺失和重置；不把无效值投入模型 |
| FR-05 | 模型选择 | 区分选择算法和选择已训练版本；校验实体、输入、硬件形态、采样与模型兼容性 |
| FR-06 | 历史训练 | 选择时间范围，预检数据覆盖和有效样本；异步训练，可取消；失败不替换在线模型 |
| FR-07 | 回放校准 | 按时间切分，无未来泄漏；展示阈值、事件、误报预算和已知标签结果，未标注部分明确说明 |
| FR-08 | 在线推理 | 增量查询并保持有界因果窗口；相同源样本不重复计时，缺口重置未完成确认 |
| FR-09 | 持续与恢复 | 正常/异常/未知分离；新鲜正常证据才恢复；模型切换、暂停与删除有管理原因 |
| FR-10 | 夜莺告警对接 | 自动建立本模块受管对象及关联；触发、恢复和测试通知可核对；不影响旧规则 |
| FR-11 | 独立 GPU 页面 | 展示 GPU 列表、同源曲线、模型结果、规则事件、质量、任务和版本；支持一致的时间与实体过滤 |
| FR-12 | 模型生命周期 | 草稿、训练、校准、验证、影子、发布、退役；版本不可变，支持回滚 |
| FR-13 | 反馈 | 真异常、正常负载变化、采集问题和未确认分别记录，不直接当自动重训标签 |
| FR-14 | 访问与审计 | 独立系统鉴权，viewer/operator/admin；所有变更有版本和操作者，不默认继承夜莺登录 |
| FR-15 | 运行健康 | 查询、任务调度、模型、结果网关、规则同步、夜莺评估与通知失败可观察 |
| FR-16 | 安装与恢复 | 配置引用已有数据源和夜莺；初始化幂等；任务、制品、结果状态和审计可恢复 |

默认提供经过验证的 GPU 任务模板，用户不需要手工编写模型结果 PromQL 或导入规则包。高级用户可定制任务输入与参数，变更需验证后生效。

## 5. 指标与数据要求

第一版先使用已有研究覆盖的温度、功耗、时钟、GPU/显存控制器利用率、显存使用等连续量；Profiling、拓扑、训练阶段是条件增强，不假定现有 Prometheus 已有。

遵守以下语义：

- `MEM_COPY_UTIL` 是显存控制器活动，不是显存容量占比；`FB_USED` 常见参考单位为 MiB，仍需现场确认。
- 百分数和 0～1 ratio 明确归一；Profiling 字段的名字含 `BYTES` 不代表一定是累计 Counter。
- Counter 先处理重置和时间窗口；时长 ns/s 转换按已有契约；XID/SXid 码值不做差分或 increase。
- 不把 ECC 汇总与分域明细相加；不把旧新同义字段当两条独立证据。
- 使用设备运行门槛而非任意固定温度；缺门槛时不伪造热余量。
- 当前实验 Prometheus 保留 3 天，不能执行超出可用历史的 14 天训练。更长数据需单独取得快照或批准保留方案。

数据、特征、模型和结果均记录来源类型 `simulated`、`replayed`、`real`；模拟 GPU 不重命名成真实 H100。详见[指标映射](04-GPU指标与检测场景映射.md)。

## 6. 非功能需求

| 方面 | 要求 |
|---|---|
| 隔离 | 模块目录、数据卷、任务和受管规则命名空间独立；旧规则仍正常执行 |
| 查询预算 | 每源超时、并发、窗口与序列数上限；预览也计入预算 |
| 容量 | 实测 GPU 数、特征数、采样和窗口后确定；当前不承诺固定集群容量 |
| 延迟 | 端到端按采集、推理、持续、夜莺评估和通知分段测量；不得沿用通用 Demo 的 8～10 秒作为生产承诺 |
| 可靠性 | 持久化任务、版本、结果水位、确认进度与告警关联；重启不能伪造持续证据 |
| 安全 | 数据源凭据服务端引用、脱敏、最小权限；模型执行依赖受控，前端不返回凭据 |
| 可维护性 | API 与模型协议版本化，迁移可回滚，升级不覆盖人工修改 |
| 可解释性 | 解释可追溯至实际指标和模型版本，不宣称因果根因 |

## 7. 范围与验收

### 7.1 本期与后续

本期目标为独立 GPU ML 系统，先实现少量有数据支撑的 GPU 检测模板及夜莺闭环；真实数据可用时再训练与旁路验证。首期物理 H100，其他型号、MIG 实例、跨集群统一控制、深度模型训练平台、夜莺插件化和自动修复均不作为首个可用版本门槛。

缺少真实硬件和历史数据时可以完成模拟、协议和回放，但真实 GPU 准入单列为阻塞生产发布的门禁，不将模拟成功写成生产成功。

### 7.2 验收层次

1. 设计：指标与检测模板对应既有台账；旧模块和新增模块边界清楚。
2. 模拟：真实 Prometheus 和夜莺链路，GPU 语义输入、四类核心场景及质量反例通过。
3. 生命周期：同一夜莺事件在未知期间保持；有效恢复、行政关闭、重启及规则升级可核对。
4. 真实旁路：实际字段、单位、拓扑、负载与误报预算得到验证。
5. 发布：新集群只配置连接和运行参数，内置适用任务自动初始化；告警先接测试出口，正式出口按现场流程启用。

相关未决信息：实际 H100 形态与 MIG、DCGM/Exporter 版本和指标样本、训练/空闲上下文、历史长度、GPU 规模、通知协议、查询及误报预算。先使用已有资料和模拟推进，不重复等待已确认的技术路线。
