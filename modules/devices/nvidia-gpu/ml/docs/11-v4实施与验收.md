# v4 DCGM场景实施与验收

日期2026-11-12，版本0.4.0。以用户“只有DCGM，没有上层作业指标”的约束实施四类场景。见[技术方案](02-技术方案.md)和[场景清单](10-DCGM场景清单与数据契约.md)。

## 实施

- dcgm-scenarios.json定义四类场景、必需指标和严格区分的production/laboratory时间profile。
- dcgm_scenarios.py实现条件残差和长窗口持续偏移/斜率；条件不匹配、缺口与窗口不足明确不可评估。
- 新场景批量配置与管理员通知授权API，默认仅证据；旧任务和源指纹保持兼容。
- Web场景入口、覆盖与不覆盖说明、profile训练窗口、残差及趋势证据。
- 新增加速热/时钟漂移注入，必须手动恢复；不新增上层模拟指标。

## 验证记录

最终结果与机器证据收尾时补充到`evidence/gpu-v4/`。旧版本证据不作为本轮自动通过依据。

## 复现

```bash
bash modules/devices/nvidia-gpu/ml/scripts/gpu-ml.sh test
docker compose -f deploy/nvidia-gpu/ml/compose.yaml exec -T gpu-ml python < modules/devices/nvidia-gpu/ml/scripts/verify_v4.py
python scripts/check_module_layout.py
```

在线脚本仅允许显式模拟环境，实际读取Prometheus历史，临时更改模拟GPU并恢复。production长期门槛验证和加速实验需要分别解释，不能外推硬件老化准确率。

## 最终实际结果

- 最终镜像gpu-monitoring-ml:0.4.0健康运行；32项核心测试通过。单目标Ridge输出形状在新增时钟场景测试中发现问题后已修复并全量复验。
- 在同一模拟GPU创建4份production参考配置和4份laboratory配置；重复提交幂等，viewer写入、真实未核验卡使用实验profile、过短生产参考历史均被拒绝。高级通用任务接口不能绕过场景profile检查，训练/发布层也有独立保护。
- 四个实验场景各从现有Prometheus取1798个有效源样本训练并发布，输入仅为DCGM字段，无job_running依赖。该计数是本次结果，不是生产训练建议。
- 默认仅证据时，条件热偏离实际被检测到，但结果网关不输出活动告警向量、没有本场景夜莺事件。管理员明确允许后，实际夜莺事件420产生；缺数期间保持，恢复新鲜可比正常历史后解除。真实Webhook触发和恢复载荷见final.json。
- 正常高负载反例通过；未见低负载返回outside_reference/窗口不可比，没有强制标成正常或硬件故障。
- 加速热漂移和时钟漂移均输出残差、残差中位数、原单位/小时斜率及1分钟窗口。本次约20秒触发是加速注入结果，绝不作为生产老化提前量、SLO或真实退化率。
- 最终镜像额外功耗/时钟关系注入通过，约8秒检测，同样仅为实验耗时。所有新场景最终恢复为仅证据、无活动条件。
- 实际重建容器后，8份场景配置的profile、通知模式及4份实验模型指针保持；一致性备份离线恢复后4份场景制品均加载和评分成功。旧源指纹和既有模型继续运行。
- 使用实际v4 API载荷通过7页DOM渲染契约测试，包含四场景卡、production/laboratory训练窗口、场景算法列表、不可用功能说明和无参考线图例。此为纯Node契约测试，浏览器视觉/点击验收仍not_run。
- 目录检查通过：45份原冻结载荷未变。

## 生产解释与后续工作

未完成真实H100长期退化效果、现场每GPU日误告警预算、真实已核验退化与正常变更对照、生产容量/HA、浏览器视觉和告警侧跨任务合并。本轮没有上层作业信息，不实现同作业慢卡、有效产出/能效或剩余寿命。默认工程时间门槛不能替代这些证据。

现场采集周期与15秒默认新鲜度不同，需要在容器环境配置GPU_ML_FRESHNESS_SECONDS以匹配采集间隔；参考采样周期与原始采集周期分开核验，不把旧样本当新鲜证据。严格连续窗口遇到缺口会不可评估，生产需实测数据覆盖和查询成本，不自动插值。
