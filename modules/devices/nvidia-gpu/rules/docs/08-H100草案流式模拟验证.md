# H100草案流式模拟验证

本指南用于无GPU机器的集成验证。模拟数据不能证明H100实际字段支持、驱动兼容或真实硬件故障处置正确。

## 1. 两层模拟测试

离线层使用promtool固定样本检查表达式：67用例、423断言。流式层由Docker Compose模拟器持续暴露指标，Prometheus每5秒抓取，夜莺每30秒评估；质量规则目标为至少持续60秒，硬件标志规则不额外延迟。夜莺9.3.0将第一次命中计作一个评估周期，因此实验适配器把质量规则原生prom_for_duration设为90秒，保证从首次命中评估到触发至少60秒。通知仅发送容器内本地接收器。

流式层使用独立路径 `/batch1/metrics`、任务 `h100-batch1-simulator`、集群 `batch1-sim-lab`、两张 `GPU-BATCH1-*` 模拟卡。modelName始终是SIMULATED-GPU；原有 `/metrics` 场景独立控制。

夜莺业务组为 **H100草案模拟验收**，8条规则名称以 `H100草案模拟-` 开头。这些是启用的实验副本；正式catalog中草案仍默认禁用。生产尚未准入。

## 2. 生成、导入与复现

现有环境已部署，无需重新执行首次安装。重建实验表达式仅在正式表达式或绑定发生变化时进行：

```bash
python3 modules/devices/nvidia-gpu/rules/scripts/build_batch1_lab.py
python3 modules/devices/nvidia-gpu/rules/scripts/build_batch1_lab.py --check
bash modules/devices/nvidia-gpu/rules/scripts/lab.sh batch1 import
bash modules/devices/nvidia-gpu/rules/scripts/lab.sh batch1 rules
```

生成器只替换集群、job、target和模拟UUID，保留阈值、30秒评估及目标60秒持续语义，并显式记录夜莺原生90秒的版本适配。文件为rules/batch1-lab-catalog.json；导入器保留已有同名规则，避免覆盖本地修改。历史时间戳及持续时间修复由 `batch1 repair` 核对旧表达式和参数后迁移，并非通用覆盖导入。

完整验收：

```bash
bash modules/devices/nvidia-gpu/rules/scripts/lab.sh batch1 suite
```

会依次改变模拟输入，检查触发/结束通知、GPU及字段身份、触发/结束hash、持续时间及旁路误报；结束或异常时恢复normal。报告保存到 `.local/reports/batch1-all.json`。完整套件最终还会审计原生trigger_time（防止通知延迟掩盖提前触发），并验证硬件缺数结束通知不宣称修复；可用 `bash modules/devices/nvidia-gpu/rules/scripts/lab.sh batch1 audit` 单独重验。勿与手工切场景同时运行。完整测试需要十多分钟，主要时间用于真实等待60秒持续条件和30秒评估周期。

可单独复现：

```bash
bash modules/devices/nvidia-gpu/rules/scripts/lab.sh batch1 suite --case smoke
bash modules/devices/nvidia-gpu/rules/scripts/lab.sh batch1 suite --case stale
bash modules/devices/nvidia-gpu/rules/scripts/lab.sh batch1 suite --case lifecycle
```

## 3. 手工验证方法

打开夜莺 <http://localhost:17000>，选择业务组“H100草案模拟验收”，查看规则及当前告警。先检查正常基线：

```bash
bash modules/devices/nvidia-gpu/rules/scripts/lab.sh batch1 state
bash modules/devices/nvidia-gpu/rules/scripts/lab.sh batch1 scenario normal
```

注入SRAM异常：

```bash
bash modules/devices/nvidia-gpu/rules/scripts/lab.sh batch1 scenario sram
```

等待约30—60秒，应出现 `sram_threshold_exceeded`，GPU为GPU-BATCH1-0000、metric_name为DCGM_FI_DEV_SRAM_EXCEEDED。随后运行：

```bash
bash modules/devices/nvidia-gpu/rules/scripts/lab.sh batch1 scenario normal
```

等待评估结束，检查历史事件和 <http://localhost:19080/batch1/events> 中本地判读通知。原始事件保留在 <http://localhost:19080/events> 供调试。标志清零仅表示测试条件退出，不证明真实硬件修复。

| 场景名 | 注入 | 预期主要规则 |
| --- | --- | --- |
| normal | 两卡四字段正常 | 无新异常 |
| sram | 第一卡SRAM标志=1 | sram_threshold_exceeded |
| remap | 第一卡重映射失败标志=1 | row_remap_failed |
| invalid | 第一卡SRAM标志NaN | required_input_invalid |
| transient_invalid | NaN持续15秒后自动正常 | 实际采到NaN，但不足60秒，不触发 |
| duplicate | 第一卡SRAM多一个replica序列 | duplicate_input_series；不下硬件结论 |
| field_missing | 第一卡SRAM字段消失 | required_field_missing |
| device_missing | 第二卡四字段消失 | expected_gpu_observation_missing；抑制逐字段告警 |
| empty | 两卡所有字段消失，HTTP成功 | 两张卡观测消失 |
| scrape_error | HTTP 503 | collector_unavailable；抑制下游缺数告警 |
| stale | 第一卡SRAM显式时间戳比场景开始早120秒 | required_field_stale |

质量规则一般需要约60—120秒才触发，不能切场景后立即判定失败。stale场景使用独立fixture_age标签避免倒序写入，开启track_timestamps_staleness使恢复时旧显式时间戳序列及时退出。配置变更后旧标签可能保留至5分钟lookback结束，自动测试会等待正常基线。

## 4. 运行引擎回归

流式联调发现原表达式在多字段timestamp时会丢失__name__，导致标签冲突。固定版本 [promqltest源码](https://github.com/prometheus/prometheus/blob/v3.2.1/promql/promqltest/test.go) 默认启用EnableDelayedNameRemoval，运行服务未启用该特性。[官方特性说明](https://prometheus.io/docs/prometheus/2.55/feature_flags/#delay-name-label-removal-for-promql-engine)解释了这种行为差异。

0.1.1逐字段对原始selector取timestamp，再用常量字段名写metric_name，最后合并；既不依赖被删除的__name__，也不对加工后的向量取timestamp。离线原样本已包含同设备相同标签，不应把此次差异归因于缺少这种标签样本。后续必须同时保留离线和真实HTTP查询/流式链路验收，不能只依赖promtool通过。

首次接入还发现up自动序列缺少cluster_id：已在独立任务static_configs中加入集群标签，不修改原有采集任务。实际现场同样需要验证target身份，不能假设Exporter指标标签会自动出现在up上。

## 5. 持续时间适配

首次持续异常验收失败：原生prom_for_duration=60、prom_eval_interval=30时，从场景注入到触发不足60秒。失败报告保留在 `.local/reports/batch1-for60-failed.json`。

固定版本[process.go](https://github.com/ccfos/nightingale/blob/v9.3.0/alert/process/process.go#L478)使用 `LastEvalTime - FirstEvalTime + PromEvalInterval >= PromForDuration`。第一次命中已计入一个周期，因此原生60秒允许两次相隔30秒的命中触发。

本实验把desired_for_seconds=60映射为原生for_seconds=90（60+30），硬件目标为0仍映射0，不增加等待。正式规则卡保存产品目标60秒，实验JSON同时记录两个值及适配原因。自动验收继续要求从注入到触发至少58秒（2秒计时容差），不放宽为30秒；这是固定版本适配，升级引擎必须重新核验。

## 6. 异常后缺数的结束语义

lifecycle场景先触发SRAM异常，再令SRAM字段消失。预期夜莺原生事件会标记is_recovered=true，同时质量规则经过60秒持续后告警。测试报告将其解释为 `input_unjudgeable_not_hardware_recovered`；本地接收器另提供 `/batch1/events`：硬件规则结束统一输出state=condition_exited、end_reason=unverified_condition_exit、hardware_recovery_confirmed=false，并明确“不能据此判断硬件修复”。原始payload保留，不篡改夜莺历史。这是实验通知契约，尚不是生产持久状态机。

因此夜莺界面的原生“恢复”仍不能作为硬件恢复承诺；实验通知判读入口已避免作此承诺。还存在质量规则pending期间的不可判定空档。生产上线前需补足持久状态与通知结束原因管理，或明确采用不含硬件恢复承诺的通知契约并通过验收。正式规则继续默认禁用。

## 7. 实际结果

2026-11-09完整验收通过：8条实验规则、11个流式用例；实际运行约19分钟。原生trigger_time审计通过，质量告警实际触发距注入约68—90秒，满足目标至少60秒。硬件异常后缺数的本地结束判读也通过审计。

[结构化验收结果](../monitoring/tests/h100_batch1-streaming-results.yaml)保存版本、摘要、耗时和结束通知语义；完整事件关联证据在 `.local/reports/batch1-all.json`。可以运行 `python3 modules/devices/nvidia-gpu/rules/scripts/summarize_batch1_lab.py` 根据通过且完成审计的报告重新生成摘要。

新增模拟器/通知契约与原有单元测试共18项通过；原有六条演示规则在新场景运行期间保持正常。最终5个Compose服务均healthy，batch1已恢复normal，8个表达式均无异常结果，测试组活动告警为0。

正式目录仍默认禁用。该结果属于合成绑定的夜莺实验副本，不把它转记为现场绑定或真实H100通过；真实H100验证仍为not_run。
