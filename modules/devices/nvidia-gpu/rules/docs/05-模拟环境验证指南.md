# 无 GPU 模拟环境验证指南

日期：2026-11-06  
当前检查点：阶段 2 的容器运行与采集已验证；阶段 3 六条规则已导入，温度触发/恢复链路通过，详见[规则导入与告警验证](06-规则导入与告警验证.md)。

## 1. 结构和边界

全部服务使用 deploy/nvidia-gpu/lab/compose.yaml 管理：GPU 模拟器 → 测试 Prometheus → 夜莺 → 通知接收器。首期夜莺及登录已由使用者确认可用；本检查点加入模拟器和接收器，尚未创建正式告警规则或绑定夜莺通知。

宿主机只需要 Docker 和 Docker Compose，Python 脚本在容器内执行。没有 GPU、DCGM 或驱动依赖。模拟器是监控输入夹具，不模拟真实硬件行为；所有 GPU 序列携带 cluster_id=gpu-sim-lab、simulated=true，并使用 GPU-SIM-0000/0001 身份与 SIMULATED-GPU 型号，避免误认为真实设备。

首批输出温度、利用率、最近 XID 错误码、volatile DBE ECC 累计值及行重映射失败标志。指标类型参考 [NVIDIA DCGM Exporter 字段配置](https://github.com/NVIDIA/dcgm-exporter/blob/main/etc/default-counters.csv)，这里只建立测试输入，真实集群仍需核对 Exporter 版本与采集配置。模拟温度 95°C 仅用于制造测试条件，不作为任何实际 GPU 型号的告警阈值。

## 2. 启动和基础验收

在项目根目录执行：

```bash
bash modules/devices/nvidia-gpu/rules/scripts/lab.sh sim-up
bash modules/devices/nvidia-gpu/rules/scripts/lab.sh scenario normal
bash modules/devices/nvidia-gpu/rules/scripts/lab.sh verify
```

已有夜莺环境时使用 `sim-up`，仅添加模拟器、接收器和测试 Prometheus，重启测试 Prometheus 使 scrape 配置生效，不拉取或重启夜莺和 Redis。全新安装使用 `up`。保留现有夜莺数据库和 Redis 卷。本环境的测试 Prometheus 可重启，不影响外部已有 Prometheus。

预期五个服务均 healthy，verify 输出两张模拟卡温度 55/56 已进入 Prometheus。检查脚本最多等待约 25 秒采集，不修改场景，不创建夜莺规则，也不证明已验证完整告警链路。

浏览器打开 http://localhost:19090，执行：

```promql
up{job="gpu-simulator"}
DCGM_FI_DEV_GPU_TEMP{cluster_id="gpu-sim-lab"}
```

前者应为 1，后者应有两条序列，UUID 分别是 GPU-SIM-0000/0001，值为 55 和 56。也可直接打开 http://localhost:19400/metrics 查看原始输出。若已在夜莺建立测试数据源，可在夜莺查询页面执行相同查询。

## 3. 场景切换验收

```bash
bash modules/devices/nvidia-gpu/rules/scripts/lab.sh scenario hot
bash modules/devices/nvidia-gpu/rules/scripts/lab.sh state
```

等待约 5–10 秒后查询温度，GPU-SIM-0000 应为 95，GPU-SIM-0001 仍为 56。然后恢复：

```bash
bash modules/devices/nvidia-gpu/rules/scripts/lab.sh scenario normal
```

| 场景名称 | 行为 | 验证重点 |
| --- | --- | --- |
| normal | 两张卡，温度 55/56，XID 为 0 | 正常基线；已有 ECC 累计值不清零 |
| hot | 第一张卡温度变为 95 | 故障只作用于一张卡 |
| xid | 第一张卡最近 XID 码变为 79 | gauge 错误码，不当作次数 |
| ecc | 第一张卡 DBE 累计值增加 1 | 每次选择增加一次，普通 scrape 不增加 |
| counter_reset | DBE 累计值归零 | 明确模拟计数器重置 |
| missing | 第二张卡全部 GPU 序列消失 | up 仍为 1，单卡缺数 |
| empty | 两张卡 GPU 序列均消失，但保留模拟器自身 info | up 仍为 1，GPU 覆盖为空 |
| scrape_error | /metrics 返回 HTTP 503 | up 变为 0，/health 和控制接口仍可用 |
| invalid | 第一张卡温度为 NaN | 无效数据，不当成温度正常或温度超限 |
| transient | 前 10 秒正常，随后高温 10 秒，再恢复 | 短暂异常，不应满足未来 30 秒持续条件 |
| sustained | 前 10 秒正常，随后高温 70 秒，再恢复 | 持续异常、触发和恢复的时间线 |

计时从选择场景开始，重新选择会重新计时。进程重启恢复 normal 且累计值归零，这个行为属于测试夹具重启边界。normal 清除 XID、温度等瞬时故障，但保留 ECC 历史累计值；需要干净计数基线时先选择 counter_reset，再选择 normal。

Prometheus 查询可能受采集周期、查询 lookback 和 stale 标记影响，切换后不要要求 UI 同一瞬间变化；采集失败时旧样本更不能被当作健康。完整缺数告警判定在下一阶段验证。

## 4. 通知接收器验收

```bash
bash modules/devices/nvidia-gpu/rules/scripts/lab.sh notify-test
bash modules/devices/nvidia-gpu/rules/scripts/lab.sh events
```

events 应显示 source=manual-smoke-test 的记录。这只证明接收器收到了手工测试请求，不代表夜莺已发送告警。浏览器也可打开 http://localhost:19080/events 查看最近 100 条记录。

后续夜莺 webhook 目标使用容器网络地址 `http://notification-receiver:9080/webhook`，不能填宿主机 localhost:19080。当前接收器接受 JSON 或文本，不收集请求认证头，单条请求限制 64 KiB。记录保存在 notification-data 卷，每个文件约 5 MiB 后轮转，保留当前及上一文件；不是生产通知队列。仅绑定本机端口，不使用真实通知账号。

## 7. 模拟器未运行的诊断

`service "gpu-simulator" is not running` 表示场景命令无法进入模拟器容器，不能单凭该消息判断是尚未创建还是启动失败。更新 Compose 文件不会自动创建新增服务，需执行 `bash modules/devices/nvidia-gpu/rules/scripts/lab.sh sim-up`。

场景命令现会在模拟器未运行时尝试单独启动它；启动失败自动展示容器状态和最近日志。这个自动启动不替代 sim-up 中的 Prometheus 配置重载。若仍失败，执行：

```bash
bash modules/devices/nvidia-gpu/rules/scripts/lab.sh diagnose gpu-simulator
```

根据完整错误区分镜像拉取、端口占用、挂载文件缺失及进程异常。不要删除数据卷或重装夜莺。
