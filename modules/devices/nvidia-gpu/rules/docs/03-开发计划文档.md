## 1. 实施原则与当前状态

按已确认的夜莺底座方案推进，先用真实指标锁定版本和扩展边界，再构建 GPU 产品发行版。当前已完成需求修订、源码调研和夜莺9.3.0无GPU实验环境，已实现模拟器、通知接收器、六条实验规则及API导入，温度触发/恢复及八个补充场景已验证（NaN修正后定向重测通过），见[模拟规则验收报告](07-首批模拟规则验收报告.md)。综合候选库和模拟故障验证已扩展，逐条状态见第10篇验收文档；正式生产规则库、真实硬件兼容、生产依赖和完整产品生命周期仍未验收。旧计划的 IR、编译器、代码生成和自研执行引擎阶段取消。

每套集群独立安装暂为默认设计，用户尚未确认集中与分散拓扑。不得等待这项选择才开始指标和单实例原型验证；集中能力另设门禁。工期需在夜莺原型和扩展范围确定后估算，不沿用旧方案工程日。

维护者负责提供和持续验证内置 GPU 规则。部署者只填写连接、身份、通知、密钥及持久化参数，不承担规则编写、导入或逐条启用工作；高级用户后续可以在线定制。选用夜莺不会取消规则，而是复用其执行和管理能力。

## 3. P0：取得H100支持验证的最小事实

第一版仅做H100，先确认PCIe/SXM/NVL形态、物理卡/实例粒度，再确认UUID、MIG GI/CI 标签、DCGM/Exporter/Prometheus 版本、实际指标样本与采样周期；同时获取集群规模、查询认证、网络限制、通知出口、持久化和 HA 期望。只读接入现有 Prometheus，不安排重新安装采集器或导入规则。

从官方 NVIDIA 依据中选择少量能被现有指标支撑的候选，记录来源版本、许可、单位、类型、适用性和期望行为。允许某集群只支持其中一部分，不能为了数量添加无依据阈值。制作正常、触发、恢复、缺数、sentinel、计数器重置、单卡消失和 MIG 变化的固定样本。对来源原生 PromQL 可用固定 Prometheus 参考求值，但不能要求用户生产实例配置参考规则。

## 4. P1：夜莺集成与扩展门禁

| 门禁 | 验证动作 | 必须提供的证据 |
| --- | --- | --- |
| G1 接入方式 | 只配置现有 Prometheus 查询地址；禁用示例采集与时序库 | 请求日志证明只读、原配置未变、无新增采集/写入 |
| G2 开箱自动化 | 空库安装后自动建源、通知及可编辑的适用 GPU 规则 | 无手工导入录像/操作记录；重复初始化无重复规则 |
| G3 在线管理 | UI/API 增查改删、启停、校验、预览与失败保留旧版 | 操作前后 revision、实际激活时间及错误信息 |
| G4 生命周期 | 本地编辑、禁用、删除后重启并升级目录 | 覆盖/tombstone 保留，冲突差异可见，全写路径有审计 |
| G5 数据和恢复 | 固定数据回放、单卡消失、重启 pending/firing、通知断网 | 每卡状态及触发/恢复时间，管理关闭与硬件恢复区分 |
| G6 运维代价 | 量化依赖、查询负载、资源、恢复及 API 稳定性 | 固定版本清单、容量数据、需维护分支和代码范围 |

P1 以夜莺为唯一原型底座，不安排 Grafana 或其他平台的并行实现。先锁定明确 release/tag、源码 commit、镜像 digest 和依赖版本，验证原生 API 后再实现最小 GPU 垂直链路：只读接入 → 自动建规则 → 触发与恢复 → 测试通知 → 在线修改 → 重启保留。

G3/G4 优先验证在夜莺规则事务层扩展 revision、审计和本地覆盖，复用原生 UI/API。列出所有写入口，证明初始化、升级、UI 和 API 都受控。若维护改动不可控，改验证外部产品库单向投影，并将夜莺受管规则入口设为只读。ADR 选定唯一方案，记录需维护文件、升级风险和工作量，不把两套写入实现带入 P2。

G6 同时产出 Apache-2.0 再分发清单：许可证、版权声明、修改说明、上游 NOTICE（如有）及第三方依赖许可；区分社区能力与另行授权的组件。许可友好不能替代功能和可靠性验收。

若门禁失败，先记录复现步骤、缺口、补足方案及维护成本。只有关键需求无法满足或维护成本不可接受时，才启动底座变更评审；不静默降低需求，也不直接转向自研通用引擎。尚未获得真实指标时可用固定样本推进原型，但不能据此宣称生产 GPU 覆盖已验证。

## 5. P2：构建最小可用发行版

实现审定目录与稳定身份、自动能力检查、幂等初始化、源及通知自动绑定、覆盖页面。规则仅在输入与适用条件满足时自动执行，缺输入明确展示；初始化失败可重试且可观察。就绪不把“没有 GPU 数据”当成全部健康。

按 P1 ADR 确定的唯一写边界实现 CRUD，不再重复选型，不保留双向随意编辑。补齐 revision、ETag、审计、desired/active_revision、apply 状态与失败重试。把用户修改持久化独立于发行镜像；新增规则草稿检查与预览成功后发布。

复用底座执行和通知，不新建重复调度器、窗口引擎或告警状态机。交付实际数据库/Redis 等配套及凭据注入，不以“单容器”掩盖依赖。

## 6. P3：完成可持续维护能力

实现目录三方合并、本地 override、禁用、tombstone、上游撤销、恢复默认和版本回滚。验证非法表达式、执行器应用失败和中途崩溃后旧版本仍可辨认且重试幂等。多规则更新显示逐条结果，不宣称底座未支持的原子提交。

删除、禁用、修改活动规则时验证停止后续通知，历史记录行政原因。演练正常恢复、pending 中途重启、长停机、firing 重启、源断网、通知断网、数据库不可用、重复发送与升级失败。固定并公开恢复语义；不满足验收的缺口必须补足或触发改选，不能用“框架已有持久化”替代实测。

备份规则库与审计；演练数据库恢复、规则内容回滚和程序回滚。 schema 不兼容时用备份恢复路径，禁止默认旧镜像能读取新数据库。

## 7. P4：真实集群验收与发布

先旁路读取真实指标，通知只接测试出口，观察覆盖与数据质量。验证最长时间窗口、一次重启、一次数据源和通知故障、设备或样本模拟变化。按 P0 预算测评估延迟、CPU/内存、Prometheus QPS 与通知延迟。查询预览也计入限额。

在第二套已有 DCGM + Prometheus 的集群使用同一发行版复装，只填写连接、身份、通知、密钥与持久化参数；不得编写规则或点导入。记录该集群型号差异及覆盖差异，证明不是靠第一套手工配置才能运行。

发布清单固定夜莺版本、扩展版本、目录摘要、正式内置规则与来源、数据库 schema、镜像 digest、许可证及已知恢复限制。运行说明覆盖首次安装、CRUD、覆盖排障、升级冲突、备份恢复、规则/系统回滚及通知失败。

## 10. 训练及生产驱动基线

用户确认H100用于训练、不启用虚拟化。设计参考采用核对日2026-11-06的最新NVIDIA Production Branch Linux补丁595.112.07，兼容条件与待核实项见[训练基线](../../common/monitoring/hardware/H100训练基线.md)。不使用浮动latest，不自动升级现有驱动/采集。MIG状态独立核对。

P0先核对现有DCGM是否满足R595要求的4.3.x及以上，再固定具体DCGM/Exporter版本；若现有采集不满足，报告兼容差异而非静默修改。多GPU训练的PCIe/NVLink/NVSwitch可靠性优先核对；利用率、显存占用和功耗高不直接归为硬件故障。

### H100流式模拟联调

已建立独立batch1采集任务、11种无GPU流式场景及8条夜莺实验规则副本。沿用正式草案30秒评估、质量条件目标60秒持续时间（夜莺9.3.0原生适配为90秒）；表达式按运行引擎行为修正，离线67用例/423断言重新通过。联调过程、复现命令与生产门禁见[流式模拟验证](08-H100草案流式模拟验证.md)。生产仍需补结束原因状态管理、真实库存/维护及H100采集准入，不能把原生恢复标志当硬件修复。


流式里程碑验收结果：8条实验副本、11场景及原生触发时间/结束语义审计全部通过；质量规则实际约68—90秒触发，已恢复normal且活动告警为0。[证据摘要](../monitoring/tests/h100_batch1-streaming-results.yaml)保留可核对版本及耗时。下一步优先评估夜莺原生恢复能力与持久状态/通知契约、真实库存及维护绑定，再推进其余H100可靠性规则；正式默认策略继续disabled，真实硬件验收not_run。


## 硬件告警保持与解除实验进展（2026-11-09）

已验证当前夜莺9.3.0 Prometheus直连路径的无数据恢复配置未生效，不能仅靠配置项认定支持。隔离实验新增只读持久状态适配器和独立Docker卷，夜莺继续承担活动事件、历史及通知；两条硬件规则在缺数/无效/陈旧/重复/采集失败时保持活动，有效唯一新鲜标志0才解除。未修改既有Prometheus采集或夜莺源码。

该适配器属于实验架构增量，未批准生产准入。继续优先评估可验证的原生恢复路径替代可能性；若保留组件，须完成真实库存/维护、备份迁移容量、行政关闭/CRUD、权限、评估通知健康与故障预算门禁。其余H100指标规则卡仍按覆盖矩阵推进，不将本实验视作全面覆盖或真实H100通过。
