# GPU 监控规则库建设方案

版本：0.2  
日期：2026-11-06  
状态：思路已确认，待取得实际指标样本并开展规则收集与验证。  
关联：[需求文档](01-需求文档.md)、[技术架构](02-技术架构文档.md)、[开发计划](03-开发计划文档.md)

## 1. 目标与原则

以夜莺作为告警底座，核心工作是建立可信、可维护的 GPU 监控规则库，并将审定规则自动配置到夜莺。维护者负责规则收集、筛选、验证和更新；部署者无需编写、导入或逐条启用规则，仅在需要定制时在线修改。

先建立 GPU 故障与异常清单，再寻找指标和候选规则，最后验证检测与告警行为。以有效覆盖为目标，不以规则数量衡量质量。优先复用夜莺原生管理、执行和通知能力，通过配置和 API 完成接入；额外开发按实际缺口评估，不将复杂平台改造作为规则库建设的前提。技术架构中版本审计等扩展仍需单独验证和排期，本方案不将其视为已有能力。

首期限定NVIDIA H100，覆盖现有 DCGM + Prometheus 能提供的数据，不新增采集要求。现有指标无法支持的检测目标仍记录在覆盖矩阵中，明确标注缺口；缺少规则或数据不代表设备健康。DCGM Exporter 只导出配置的遥测字段，官方存在的字段不代表现场已采集。

## 2. 建立覆盖矩阵

以“需要发现什么问题”为主线，每行对应一个检测目标，记录候选规则、依赖指标、适用设备、验证状态和覆盖缺口。

| 分类 | 重点检查 | 默认策略建议 |
| --- | --- | --- |
| 硬件与可靠性 | 不可纠正 ECC、行重映射失败、需关注的 XID | 依据明确且输入满足时启用 |
| 温度与运行限制 | 温度异常、热降频、异常功耗限制 | 根据型号和设备能力判断 |
| 互联与通信 | NVLink 错误、链路异常、PCIe 异常 | 有对应指标与拓扑依据时启用 |
| 容量与效率 | 显存压力、持续低利用率、负载不均衡 | 可选策略，结合业务配置 |
| 监控自身健康 | 采集失败、单卡消失、指标陈旧或无效 | 默认纳入，区分监控异常与硬件异常 |

覆盖矩阵同时区分已覆盖、不适用、缺少输入、待验证和当前不可检测。默认策略是建设方向，不表示已有规则通过验证。

## 3. 按证据等级收集候选

| 来源 | 主要用途 | 使用要求 |
| --- | --- | --- |
| NVIDIA 官方资料 | 确认字段语义、适用性、故障解释与处置 | 记录文档版本、链接和适用范围 |
| 开源实现 | 参考表达式、时间条件、部署方式 | 记录来源版本与许可，核验后再纳入 |
| 现场经验 | 补充漏报场景、调整持续时间与通知优先级 | 关联脱敏故障记录、工单或观测证据 |

社区规则只作为候选，不直接默认启用。同一故障的多个实现合并到同一检测目标，保留参考来源和差异。XID 可能涉及硬件、驱动或应用问题，不统一解释为 GPU 硬件损坏；错误码不作为次数计数器使用。

## 4. 规则卡规范

收集结果必须能够解释、验证和维护，不能只有规则名称与 PromQL。

| 内容 | 必须记录的信息 |
| --- | --- |
| 身份与分类 | 稳定 rule_id、名称、检测分类、规则版本和维护状态 |
| 检测目标 | 异常现象、可能影响及检测边界 |
| 依据与来源 | 官方依据、参考实现、来源版本与许可 |
| 适用范围 | GPU 型号/架构、DCGM/Exporter 版本、MIG 模式等限制 |
| 输入要求 | 指标、标签、单位、类型和稳定设备身份 |
| 判断逻辑 | 表达式、阈值、评估周期、窗口、持续及恢复条件 |
| 异常输入处理 | 缺数、陈旧、无效值、查询失败及计数器重置策略 |
| 通知与处置 | 严重度、通知摘要、建议检查步骤及责任对象 |
| 验证情况 | 样本、预期结果、执行结果、已知误报与漏报 |

字段名称、语义、类型及单位须与实际版本匹配；不能直接将最新版文档中的字段套用到所有集群。温度阈值需有设备或型号依据；高利用率和高显存占用不默认视作硬件故障。

## 5. 准入与发布状态

默认启用规则须同时满足：

- 依据明确，能解释告警条件与风险的关系。
- 现场输入满足，指标、标签、单位和设备身份匹配。
- 告警可处理，有明确检查步骤和责任对象。
- 正常、触发、恢复及异常输入行为均已验证。
- 默认参数合理，不依赖未经验证的跨型号统一阈值。

| 发布状态 | 定义 |
| --- | --- |
| 默认启用 | 已验证，系统能够自动判断适用条件；输入与条件满足时启用 |
| 可选启用 | 需要业务背景或现场阈值，如低利用率和容量策略 |
| 待验证 | 保留资料与候选实现，不参与默认生产告警 |

规则发布状态与某台设备的实际覆盖状态分别记录。默认启用规则也可能因某设备缺少输入而无法执行，必须展示原因。

## 6. 验证方法

### 6.1 固定样本验证

每条规则至少覆盖正常、触发、恢复、缺数和无效值。累计值相关规则增加计数器重置；设备相关规则增加单卡消失、设备替换和 MIG 变化。记录时间序列输入、预期触发/恢复时间及实际结果。

验证分为表达式逻辑检查与夜莺实际执行检查，后者须核实持续条件、触发/恢复、通知内容及稳定设备身份。不能仅凭表达式返回结果就认定整条告警链路通过。

不主动制造硬件故障，优先使用历史数据及合成样本。无法取得某类真实故障样本时明确标注验证程度。

### 6.2 现场旁路观察

只读查询真实 Prometheus，先接测试通知渠道。逐条确认告警合理性，记录误报原因、重复通知、缺失输入和处置可行性，再调整默认策略。

运行期间没有告警不能证明规则有效。现场观察与固定样本证据共同决定准入，未验证范围保留为已知限制。

## 7. 分批推进

| 批次 | 重点 | 交付结果 |
| --- | --- | --- |
| 第一批 | 监控健康、严重内存错误、行重映射、重点 XID、热异常 | 一套数量适中、依据充分的默认规则 |
| 第二批 | NVLink/PCIe、更多型号及 MIG 场景 | 扩大硬件与互联覆盖，补齐兼容矩阵 |
| 第三批 | 显存压力、利用率、负载不均衡等 | 按业务场景提供可选规则包 |

第一批先取得实际指标与标签样本，建立覆盖矩阵和候选台账，选择少量高价值规则完整走通收集、审定、样本验证、夜莺执行和现场观察流程，再扩大范围。不提前承诺规则数量或所有 GPU 故障均可检测。

## 8. 交付物与计划衔接

交付内容包括覆盖矩阵、候选规则台账、审定规则目录、逐条规则卡、验证样本与记录、型号/版本兼容矩阵、处置说明及已知缺口。夜莺规则配置由审定内容生成或转换，转换方式在集成阶段确定，不另建通用规则编译器。

对应开发计划：P0 收集实际输入并建立矩阵和首批候选；P1 用少量规则走通夜莺链路；P2 扩充审定目录并实现自动配置；P3 验证更新保护与异常行为；P4 进行现场观察和第二集群复装。规则库版本与系统版本分别记录，更新须保留用户定制。

## 10. 文档格式确认与首份样例

2026-11-06 已确认采用“指标说明卡 + 规则说明卡 + 覆盖矩阵”，并以Markdown详细说明、YAML结构化定义和固定样本共同维护。入口见[monitoring/README.md](../monitoring/README.md)。

当前只编写ECC累计指标及近期新增错误规则各一份完整样例，等待内容深度审阅后再批量展开；样例是draft+disabled，不修改现有六条实验规则。离线表达式样本通过不等于夜莺新表达式或真实硬件验收通过。

## 11. H100优先的型号边界

第一版只做H100。指标和规则均增加型号配置兼容矩阵，PCIe/SXM/NVL及MIG差异分别记录；H200等其他型号后续再扩展。官方能力、官方故障/诊断条件与本项目告警参数分开标注。范围及结构化记录见[H100文档](../../common/monitoring/hardware/H100.md)和[hardware.yaml](../../common/monitoring/catalog/hardware.yaml)。

## 12. H100训练场景约束

第一版用于训练、不启用虚拟化；以物理GPU为监控对象，不建设vGPU/虚拟机专用规则。Linux生产驱动参考版本为595.112.07，具体兼容条件见[训练基线](../../common/monitoring/hardware/H100训练基线.md)。MIG开关不从无虚拟化推断。训练效率类策略需要作业上下文；训练高负载不直接触发硬件故障告警。

## 13. 首版覆盖与候选台账

2026-11-09已建立24检测目标、92候选输入及33规则/检查/策略提案的互相引用。机器可读定义与阅读入口见[monitoring总览](../monitoring/README.md)。类型、单位、字段ID与别名以固定源码和CSV记录；实际H100支持/采集均仍待核实，台账条目不是已发布覆盖。

XID源快照的78个H100适用码已逐项登记，处置一律pending_review，不能按适用性直接生成呼叫告警。所有提案保持disabled且没有执行表达式，正式建卡后再进行输入分组、参数审定及分层验证。


## H100首批卡片实施进展（2026-11-09）

已新增5份输入卡和8条默认禁用草案，包括采集失败、设备观测消失、字段缺失/陈旧/无效、重复采集、SRAM超阈值和行重映射失败。当前合计6份输入卡、9条草案；原有与本批合计67用例/423断言离线通过。[验收记录与验证方法](../monitoring/tests/h100_batch1.md)列出实际证据和边界。此前1/1统计为台账初版历史状态。

此批使用合成库存绑定，未导入夜莺，未验证真实H100。下一步完成测试环境绑定与夜莺持续时间、抑制、通知和结束原因联调；输入失效不能误报硬件恢复。生产型号准入、库存维护绑定及平台自身健康仍为未完成门禁。


### H100流式模拟联调

已建立独立batch1采集任务、11种无GPU流式场景及8条夜莺实验规则副本。沿用正式草案30秒评估、质量条件目标60秒持续时间（夜莺9.3.0原生适配为90秒）；表达式按运行引擎行为修正，离线67用例/423断言重新通过。联调过程、复现命令与生产门禁见[流式模拟验证](08-H100草案流式模拟验证.md)。生产仍需补结束原因状态管理、真实库存/维护及H100采集准入，不能把原生恢复标志当硬件修复。


流式里程碑验收结果：8条实验副本、11场景及原生触发时间/结束语义审计全部通过；质量规则实际约68—90秒触发，已恢复normal且活动告警为0。[证据摘要](../monitoring/tests/h100_batch1-streaming-results.yaml)保留可核对版本及耗时。下一步优先评估夜莺原生恢复能力与持久状态/通知契约、真实库存及维护绑定，再推进其余H100可靠性规则；正式默认策略继续disabled，真实硬件验收not_run。


## 硬件告警保持与解除实验进展（2026-11-09）

已验证当前夜莺9.3.0 Prometheus直连路径的无数据恢复配置未生效，不能仅靠配置项认定支持。隔离实验新增只读持久状态适配器和独立Docker卷，夜莺继续承担活动事件、历史及通知；两条硬件规则在缺数/无效/陈旧/重复/采集失败时保持活动，有效唯一新鲜标志0才解除。未修改既有Prometheus采集或夜莺源码。

[设计与验证方法](09-硬件告警保持与解除策略.md)、[验收结果](../monitoring/tests/hardware-lifecycle-results.yaml)记录9个状态用例、上游查询失败、适配器和夜莺真实重启均通过。新增12个解除判据用例，离线累计79用例/447断言；单元/HTTP测试25项通过。

该适配器属于实验架构增量，未批准生产准入。继续优先评估可验证的原生恢复路径替代可能性；若保留组件，须完成真实库存/维护、备份迁移容量、行政关闭/CRUD、权限、评估通知健康与故障预算门禁。其余H100指标规则卡仍按覆盖矩阵推进，不将本实验视作全面覆盖或真实H100通过。


## ECC 和 XID 草案进展（2026-11-11）

已补齐 ECC 汇总、设备内存及 SRAM 的统计域对照，并完成 78 个 XID 的逐码处置草案。8 条 ECC 诊断查询和 2 条 XID 复核查询通过 90 个合成用例。现场字段绑定、XID 有序事件及通知仍待验证。详见[统计域与逐码分级](../monitoring/ecc-xid-review.md)。


## 维护、温度、降频与互联进展（2026-11-11）

已新增 15 条默认禁用复核查询，包括行重映射 pending、GPU/HBM 设备运行温度余量、6 类时钟原因、未知位检查、热限制时长秒制换算、PCIe replay 和 Hopper NVLink CRC/recovery/replay。138 个离线用例及 8 个独立 Prometheus 流式场景通过。当前离线累计 307 用例和 675 项断言。

现场温度门槛、持续和分级参数、预期端口及作业清单、NVSwitch/Fabric Manager 遥测仍待核验和实现。夜莺通知和真实 H100 适配待验收。详细判据、输入映射及手工验证见[本批文档](../monitoring/thermal-links-review.md)。
