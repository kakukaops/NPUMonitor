# 硬件告警保持与解除策略

日期：2026-11-09。范围：H100训练规则的隔离实验，真实H100与生产准入未完成。

## 1. 需要解决的问题

普通表达式无结果可能表示标志解除，也可能表示字段消失、值无效、数据过期、重复采集或查询失败。只把夜莺恢复通知改成“条件退出”仍不足以保持活动事件。本批目标是：异常一旦确认，缺少可用解除证据时保持同一条夜莺活动事件；有效标志0才解除。

“解除”仅表示检测标志已解除，不能解释为硬件已修复或符合RMA结论。

## 2. 原生能力实测

固定版本flashcatcloud/nightingale:9.3.0，使用当前Prometheus直连规则路径。独立业务组“H100恢复策略实验”的临时探测规则配置 `recover_config.judge_type=1`（NotRecoverWhenNoData），API回读一致；先注入SRAM=1，再移除字段，仍收到1条原生恢复通知，活动事件消失。

固定版本[模型定义](https://github.com/ccfos/nightingale/blob/v9.3.0/models/alert_rule.go)包含该枚举，但[评估实现](https://github.com/ccfos/nightingale/blob/v9.3.0/alert/eval/eval.go)的GetPromAnomalyPoint路径没有向异常点赋该恢复配置；[处理器](https://github.com/ccfos/nightingale/blob/v9.3.0/alert/process/process.go)依赖异常点里的配置控制恢复。此结论只适用于本次镜像与执行路径，不代表夜莺所有数据源或未来版本不支持显式恢复。

探测报告为 `.local/reports/recovery-native-probe.json`，临时规则保留为禁用状态。升级版本或切换原生查询路径后应重新探测，优先采用经实测的原生能力。

## 3. 最小实验适配

新增Compose服务 `recovery-adapter`，使用已有Python固定镜像与标准库SQLite，状态保存到独立 `lifecycle-data` 卷。它只读现有Prometheus HTTP查询，不写入Prometheus，不新增采集任务，不修改夜莺源码。

该组件只承接两条硬件布尔规则的保持与解除：SRAM超阈值、行重映射失败。夜莺继续承担活动事件、历史和本地测试通知。专用Prometheus类型数据源为“H100恢复状态-只读适配器”，连接仅用于固定查询，不替换既有数据源。原有八条无状态实验规则保留作对照；真正验证保持行为时查看“H100恢复策略实验”中的“持久恢复实验-”规则。

链路为：既有Prometheus → 有效标志判据 → SQLite持久状态 → 夜莺固定查询 → 本地通知接收器。

适配器提供两条固定Prometheus查询接口，供夜莺使用；它不是通用Prometheus或任意PromQL代理。另支持夜莺连接校验所需的固定 `1+1` 探测。历史查询、任意表达式、生产绑定不在本批范围内。

## 4. 状态和转换

身份键为rule_id + cluster_id + UUID + metric_name。实验集群及两个GPU身份写入固定绑定文件，未知设备不能凭空加入。输出标签保持稳定，不把quality或last_value放入活动事件标签，避免因标签变化结束并重建事件。

| 原状态 | 本次证据 | 新活动状态 | 数据质量 |
| --- | --- | --- | --- |
| 非活动 | 有效、新鲜、唯一标志1 | 活动 | valid |
| 活动 | 有效、新鲜、唯一标志1 | 保持活动 | valid |
| 活动 | 有效、新鲜、唯一标志0 | 解除 | valid |
| 活动 | 无有效结果，包括缺数、NaN、过期或重复 | 保持活动 | unjudgeable |
| 活动 | 查询异常、警告或返回身份异常 | 保持活动 | query_error |
| 非活动 | 尚无有效输入 | 不伪造硬件异常，但不可当作健康 | unverified/unjudgeable/query_error |

有效证据直接复用本批已审阅规则：已登记设备、采集up正常、原始样本年龄0—90秒、输入唯一、枚举精确为0或1。解除表达式仅把对应硬件标志比较从1改为0，其他guard相同。规则和绑定生成器为 `modules/devices/nvidia-gpu/rules/scripts/build_recovery_lab.py`，输出 `modules/devices/nvidia-gpu/rules/rules/recovery-lab.json`。

SQLite中保存active、quality、last_value、last_valid_at、last_attempt_at和转换记录。last_valid_at是有效证据求值时间，并非原始GPU样本时间；原始时间由查询guard核验。查询失败、缺数和重启不会重置active。

### 输出数据契约

输出名 `gpu_lifecycle_active` 是派生告警状态，不是GPU实时测量，也不是新采集的官方DCGM字段。单位为布尔活动状态；只为active=1的登记对象返回值1，非活动对象不返回向量。首次缺数且没有异常历史时也可能无活动向量，必须结合/state的quality判断，不能据此判健康。

输出标签为cluster_id、UUID、metric_name、lifecycle_rule_id、simulated，均用于稳定身份；输出时间戳是本次状态查询时间，不能当作原始GPU采样时间。原始输入仅经既有Prometheus查询读取，未写入或替换GPU指标。上游查询、状态和夜莺事件三层证据分别保留。

## 5. 失败和重启约定

数据库必须显式初始化。服务启动只允许打开已存在且schema/绑定摘要匹配的库，拒绝自动创建、覆盖或改变设备清单。状态库丢失、损坏、配置不匹配或轮询心跳超过30秒时，查询返回错误，不能返回成功空向量。

数据库采用事务保存转换，每次读写核对schema、绑定摘要、预期对象和枚举值，避免运行中状态库替换造成成功空结果。适配器停止时夜莺查询失败；本批必须实测既有活动事件不会因此结束。重启后从原卷恢复，仍然缺数时继续保持活动，直至有效标志0。

健康检查说明服务与状态库/轮询是否可用；上游采集质量另见 `/state` 中quality。初次安装没有硬件异常历史时，缺数不会虚构已有硬件事件，仍依赖原有质量告警。这不是“没有活动告警就健康”。

## 6. 启动和验证

当前实验环境由代理执行部署。全新安装才执行初始化，已有状态库再次初始化会拒绝，不能删除卷来强行继续：

```bash
python3 modules/devices/nvidia-gpu/rules/scripts/build_recovery_lab.py
bash modules/devices/nvidia-gpu/rules/scripts/lab.sh recovery-init
docker compose -f deploy/nvidia-gpu/lab/compose.yaml up -d --wait recovery-adapter
bash modules/devices/nvidia-gpu/rules/scripts/lab.sh recovery install
```

日常查看与测试（重启演练会短暂中断实验环境服务，并带自动恢复）：

```bash
bash modules/devices/nvidia-gpu/rules/scripts/lab.sh recovery state
bash modules/devices/nvidia-gpu/rules/scripts/lab.sh recovery suite
bash modules/devices/nvidia-gpu/rules/scripts/test_recovery_restart.sh
```

浏览器打开 <http://localhost:19410/state> 查看持久状态；夜莺 <http://localhost:17000> 选择“H100恢复策略实验”。手工顺序：

1. 执行 `bash modules/devices/nvidia-gpu/rules/scripts/lab.sh batch1 scenario sram`，等待持久规则触发，记录活动事件ID。
2. 执行 `bash modules/devices/nvidia-gpu/rules/scripts/lab.sh batch1 scenario field_missing`，等待至少40秒。该持久规则应保持同一活动事件，/state应为active=1、quality=unjudgeable。
3. 执行 `bash modules/devices/nvidia-gpu/rules/scripts/lab.sh batch1 scenario normal`，收到有效标志0后事件才结束。此处表示模拟标志解除。

实验适配器每5秒轮询，夜莺两条持久实验规则每5秒评估、for=0。它们独立于上批30秒评估/质量目标60秒的实验规则，不把这些新参数说成正式生产参数。

## 7. 验收与未完成门禁

测试覆盖：活动后缺字段、NaN、重复、陈旧、HTTP503、全卡消失时保持原事件ID/hash且不发送恢复通知；有效0后解除；SRAM和重映射规则分别核验；真实适配器停机/重启保持状态。结构单元测试还覆盖状态库丢失、运行期间绑定替换、重复初始化、过期/未来轮询心跳以及返回身份/枚举/重复/警告拒绝；真实HTTP测试覆盖GET、POST、固定标量校验及存储错误返回503。

2026-11-09实际通过：

- 2条持久规则、9个保持/解除用例通过；SRAM连续6种不确定输入下保持事件ID=76，重映射规则事件ID=78也保持至有效0。
- 上游查询中断约24秒、适配器停机约20秒、适配器及夜莺真实重启均未解除事件ID=86；恢复有效0后才结束。
- 新增解除判据12用例/24断言通过；累计离线79用例/447断言通过。
- 模拟器、接收器、状态及真实HTTP契约共25项单元测试通过。
- 最终6个Compose服务healthy，场景normal，4个持久状态均valid/非活动，3个实验业务组无活动告警。

[结构化验收结果](../monitoring/tests/hardware-lifecycle-results.yaml)保存绑定、事件ID/hash、故障持续时间和报告摘要。[解除判据离线结果](../monitoring/tests/hardware-lifecycle-promtool-results.yaml)独立记录固定样本证据。完整原始记录位于 `.local/reports/recovery-lifecycle.json`、`recovery-restart.json`、`recovery-native-probe.json`。

最后检查发现禁用的临时探测规则仍有残留活动记录，已核对其本次创建的ID/hash/归属后归档并清理；原生恢复历史仍保留。该动作记录为administrative_lab_cleanup_not_hardware_recovery，不作为硬件解除证据。事件列表过滤参数已按固定版本核实为bgid，先前gids会被忽略；测试另有rule_id筛选，结果未依赖错误的组总数。

两条规则的输入、状态和原生事件分别验证，没有沿用上一批无状态测试结果。
