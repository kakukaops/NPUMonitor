## 交付原则更新

按用户确认，真实GPU数据不作为规则模块研发、软件验收和首个生产发行版交付的强制前置条件。使用明确版本的指标契约、固定参数和模拟数据，驱动正式版本的Prometheus、状态组件和夜莺，完成可重复的端到端验收。

“确定”是指已约定版本、字段、单位、枚举、身份和参数后的执行逻辑可确定验证；来源表中工程参数仍标明工程选取，不能改写为官方统一门槛。合成测试可以证明软件在契约条件下的触发/恢复行为，不据此宣称已测真实硬件故障检出率。

上线兼容检查由产品自动执行：核对实际数据源的字段、标签和能力是否满足契约，满足者启用，不满足者显示缺口。研发不等待用户人工提供真实数据；预检功能本身也使用模拟成功/失败样本验收。

当前生产未就绪的原因是执行、集成、故障恢复和发行封装尚未完成，不是缺少真实GPU或真实业务样本。原计划中的真实数据旁路改为部署后的可选观察和参数优化，不阻塞软件交付。

## 4. 实施次序与交付配置

1. 先完成R01的版本化契约、模拟样本矩阵与预检工具，以及R02的规则白名单和确定判据。无需真实GPU或业务任务信息。
2. 补齐R03—R05的生产执行链路及只读资产/恢复路径，使“配置→规则→状态→夜莺”真正可运行。
3. 完成R06—R08的通知、故障测试及可安装发行版，保留受控旧版本和回滚能力。
4. 完成R09—R10的模拟容量、恢复演练与运维交付，形成可安装生产版本；实际部署按预检结果启用适用白名单。

可立即在仓库推进：预检工具、生产身份/状态接口、静态清单编译、夜莺同步/回滚、隔离端到端测试、CI与安装封装。

交付软件无需用户提供真实时序数据。部署时只需配置数据源/夜莺地址与认证、采集job范围、通知出口，以及所启用可选功能需要的OS资产/拓扑信息；字段与标签能自动检查的由预检完成。开发阶段以隔离模拟数据源和测试通知出口完成相同流程。真实硬件验证继续如实记为not_run，但不作为软件发行阻塞项。

## 5. 首发通过标准

部署者不写PromQL、不手工逐条导入，也不需要添加业务标签。配置现有数据源、夜莺、通知和可选OS资产后：

- 预检逐条判断适用性并展示缺口；只有白名单且输入有效的规则可执行。
- 触发、持续确认、未知保持、恢复和通知均有新版本实际证据；数据源或组件失败不会被解释为硬件恢复。
- 状态重启和备份恢复可验证，更新失败保留旧版；权限、凭据及操作审计可检查。
- 在声明规模的模拟指标负载下通过链路及容量验收，兼容范围、工程参数、处置流程和上线预检行为明确；不宣称已做真实硬件故障验证。

审计当前状态为未通过上述生产标准，不能只将default_policy从disabled改成enabled视为完成。

## 6. 模拟验收矩阵

| 层次 | 模拟输入/故障 | 实际运行的组件与验收点 |
|---|---|---|
| 指标契约 | 字段别名、单位、枚举、身份、MIG排除、重复及缺失 | 真实预检/规范化代码，正确识别支持、缺口和未知 |
| 表达式 | 正常、阈值边界、瞬时与持续异常、计数器复位、NaN/Inf/sentinel、陈旧及未来时间 | 正式Prometheus/promtool，逐规则结果符合固定规范 |
| 告警生命周期 | 持续时间不足/满足、中途缺数、有效恢复、人工确认、旧样本重放 | 新状态组件与正式夜莺，检查pending/firing、事件关联、未知保持及恢复 |
| 通知 | 告警/恢复、发送失败、重试、重复投递和静默 | 真实发送代码与可控HTTP测试接收端，不以函数桩代替完整调用 |
| 运行故障 | 数据源超时/HTTP错误、状态组件/夜莺重启、存储失败、规则更新失败 | 正式组件和隔离持久卷，验证不会误清除、丢状态或覆盖旧有效版本 |
| 容量 | 多节点、多GPU、多规则、不同采样频率及异常比例 | 正式查询/执行链路，记录资源、QPS、延迟及恢复时间 |

现有53个PromQL用例是此矩阵的一部分；“使用模拟数据即可验收”不等于只验证单点越阈值，也不等于可以省略34项硬件观测的生产执行实现。
