# 夜莺规则导入与告警验证

日期：2026-11-06  
当前状态：六条实验规则已通过API导入并回读，重复导入未产生重复规则；温度规则触发和恢复通知的完整链路已通过，测试后已恢复normal。其余五条规则及短暂异常、计数器重置均已完成模拟验收，NaN用例修正后通过定向重测；详见[验收报告](07-首批模拟规则验收报告.md)。

## 1. API 凭据

在夜莺管理员账号的个人设置中创建测试 API Token，单独保存到项目根目录 `.local/n9e-token`，文件只包含 token。不要贴到聊天、命令参数或提交版本库。`.local/` 已加入 `.gitignore`，目录权限设置为700；建议将token文件权限设置为600。

导入器通过只读挂载读取这一文件，不打印token，不直接读取或修改夜莺数据库。需要管理员token是因为初始化包含创建专用数据源；后续可拆分初始化和普通规则管理权限。个人API Token仍继承账号权限，完成测试后可撤销。

## 2. 自动导入

```bash
bash modules/devices/nvidia-gpu/rules/scripts/lab.sh check-rules
bash modules/devices/nvidia-gpu/rules/scripts/lab.sh import-rules
bash modules/devices/nvidia-gpu/rules/scripts/lab.sh rules
```

自动创建专用测试用户组、GPU模拟实验业务组、GPU模拟-Prometheus数据源、GPU模拟-本地Webhook媒介及GPU模拟-通知规则。只接入容器内Prometheus，只通知容器内接收器。导入适配器以固定版本源码为依据，需要运行验证后才能认定API兼容。

重复导入按名称查找并回读，不重复创建；现有规则保留修改、禁用状态，不自动覆盖。专用通知地址不符时停止。同名实验对象冲突需要人工检查；本阶段尚未提供删除tombstone和规则升级合并，手工删除后再次导入可能重建，不宣称已实现生产升级保护。

首批六条规则及适用边界见[规则目录](../rules/README.md)。这些是实验规则，不能直接当作生产默认规则库。

## 3. 页面验收

打开 http://localhost:17000：

1. 在业务组中选择“GPU模拟实验”。
2. 在告警规则列表确认有六条“GPU实验-”规则，数据源为专用模拟Prometheus。
3. 查看温度规则：测试阈值85°C、评估周期5秒、持续30秒、恢复通知开启。
4. 查看通知配置：专用Webhook地址为 http://notification-receiver:9080/webhook，没有真实外部渠道。
5. 再次导入后数量应保持六条，手工修改或禁用的已有规则不会被覆盖。

## 4. 触发与恢复验证

```bash
bash modules/devices/nvidia-gpu/rules/scripts/lab.sh scenario normal
bash modules/devices/nvidia-gpu/rules/scripts/lab.sh e2e
```

e2e会切换为hot，等待接收器收到夜莺温度触发通知，切回normal，等待同一告警实例的恢复通知。核对UUID为GPU-SIM-0000、模拟标记以及触发持续时间，最终恢复normal。每段最多等待150秒。运行时不要同时手工切换场景或运行另一份测试。

结果保存在 `.local/reports/e2e-temperature.json`。只有 passed=true 且没有 cleanup_failed，才能记为本次完整链路通过。它不等于所有六条规则均已通过故障用例，也没有证明真实硬件恢复。后续仍需分别验证短暂异常、缺数、NaN、ECC重置等场景。

手工方式：选择hot后等待约40–90秒，夜莺活动告警中应出现第一张模拟卡的温度告警，接收器 /events 中有 is_recovered=false。恢复normal后等待恢复通知，is_recovered=true。实际时延需记录，不承诺页面在精确第30秒更新。

## 5. 故障诊断

```bash
bash modules/devices/nvidia-gpu/rules/scripts/lab.sh diagnose nightingale
bash modules/devices/nvidia-gpu/rules/scripts/lab.sh events
bash modules/devices/nvidia-gpu/rules/scripts/lab.sh rules
bash modules/devices/nvidia-gpu/rules/scripts/lab.sh alerts
```

`alerts` 会分别显示当前活跃告警和最近24小时历史记录，便于区分测试结束后的自动恢复与没有触发。

区分规则未导入、规则禁用、数据源绑定错误、评估尚未开始、通知规则未匹配、发送失败等原因。不要通过清空数据库或关闭认证绕过问题。共享日志前检查并去除凭据和个人信息。

## 6. 本轮运行结果（2026-11-06）

- 业务组：GPU模拟实验，ID=2；专用数据源ID=1；通知规则ID=1。
- 六条规则ID=1..6，均启用，并绑定本地通知规则。重复导入保留全部现有对象，数量仍为六条。
- 温度场景切换至hot后约33秒观察到触发通知，UUID=GPU-SIM-0000；恢复normal后约6秒观察到恢复通知，两者hash一致。
- 报告 `.local/reports/e2e-temperature.json` 中 passed=true，无清理失败；测试后两卡温度55/56，六条表达式正常基线均不命中。
- 夜莺first_trigger_time表示首次进入firing的时间，不是pending起点；恢复通知沿用原trigger_time。因此测试以场景时间检查早触发，以接收器received_at区分本轮通知，再用hash关联触发与恢复，不能用两种通知的trigger_time差值计算恢复延迟。
- 前期测试脚本对上述时间字段的误判已修正。本轮只认最终通过报告，不将脚本误判当作夜莺故障。

这是模拟链路验证，不是生产规则验收；短暂异常、缺数、NaN、ECC重置及真实硬件适用性仍需继续验证。

## 7. 页面验收时保留活动告警

自动e2e会在结束时恢复normal，所以活动/活跃告警列表可能为空，已结束的触发与恢复记录应在历史告警中查看。用户反馈看不到告警后，已通过API确认历史记录存在，并重新选择hot保留现场供页面验收。请在活跃/当前告警页面选择“GPU模拟实验”，清除其他业务组、数据源或级别筛选并刷新；历史记录选择最近24小时。

现场验收结束后执行 `bash modules/devices/nvidia-gpu/rules/scripts/lab.sh scenario normal` 恢复。保留hot期间不运行normal基线检查或自动e2e，以免改变验收现场。

## 8. 多场景自动验收

```bash
bash modules/devices/nvidia-gpu/rules/scripts/lab.sh suite
```

运行前须处于normal，且不要同时手工切换场景。suite通过API读取实际活动告警、通过本地接收器观察真实夜莺通知，不改规则阈值，也不直接伪造告警记录。场景顺序为transient、xid、ecc、counter_reset、scrape_error、missing、empty、invalid。

每个正向故障用例核对预期规则和UUID的触发及恢复通知、两者hash一致，以及是否出现其他实验规则的旁路误报。transient用例确认真实采到高温后仍无告警；counter_reset用例在ECC近期新增窗口已退出后检查重置不产生新告警。ECC恢复依据是一分钟窗口内已无新增，不是硬件修复。missing和empty分别期望一张及两张卡指标消失；scrape_error仅期望采集失败告警，不应同时生成设备消失告警。

测试约需数分钟，失败即停止后续场景并尽可能恢复normal。报告保存在 `.local/reports/e2e-scenarios.json`，应同时检查顶层passed、每个case的passed及cleanup_error。运行完成后在夜莺历史告警中选最近24小时及“GPU模拟实验”，查看不同规则与UUID。活动列表可能因测试自动恢复而为空。

本套测试不覆盖：从未发现设备、超过10分钟保留窗口、Inf或DCGM特殊值全集、查询断网、规则变更/进程重启恢复，以及真实型号适用性。这些不能由本套模拟测试的通过结果推断。

无效温度规则在首轮多场景测试中发现返回NaN无法形成预期夜莺告警，已将目录升级至lab-0.1.1，使用bool比较并筛选结果=1。升级命令为 `bash modules/devices/nvidia-gpu/rules/scripts/lab.sh repair-invalid`，定向复测命令为 `bash modules/devices/nvidia-gpu/rules/scripts/lab.sh suite --case invalid`，复测报告独立保存至 `.local/reports/e2e-scenarios-invalid.json`；不得用定向复测结果掩盖首轮失败记录。
