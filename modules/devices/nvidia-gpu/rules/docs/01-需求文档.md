## 1. 背景与目标

现有 GPU 集群已经部署 DCGM + Prometheus，指标采集已完成。用户需要一个独立、可重复部署的告警系统，直接查询这些已有数据，在新集群上只填写连接及运行参数即可开始告警。

**部署者无需配置 Prometheus 告警规则，无需导入规则包、模板或 PrometheusRule，无需重新部署采集。** 系统内部如何存储和执行规则属于实现细节。系统应内置经过核实的 GPU 检测逻辑，并允许授权用户在需要时通过界面及 API 增删改查。默认无需管理规则与后续可以管理规则是两个同时成立的要求。

交付物是包含内置 GPU 能力的完整系统发行版及一键部署配置，而非规则文件集合。完整系统可以复用开源平台，并包含必要数据库等依赖；不要求只有一个进程或一个容器。

第一版GPU型号范围已于2026-11-06确认为 **NVIDIA H100**。H200及其他型号后续扩展；H100的PCIe/SXM/NVL形态、软件栈和MIG模式需逐项核实，不承诺同一阈值适用于所有H100配置。型号与指标/规则兼容性记录见[H100范围](../../common/monitoring/hardware/H100.md)。

## 3. 使用流程与边界

首次部署只提供 Prometheus 地址与认证引用、稳定 cluster_id、通知出口、管理员凭据及持久化参数。系统验证连通性，读取实际指标和设备信息，初始化可编辑的规则对象，自动启用满足条件的内置规则，显示实际覆盖。缺少某项指标不阻止其他已支持规则运行，也不自动认定 GPU 健康。数据源不可达或尚未发现设备时显示接入失败或未发现设备，不显示“全部正常”。

后续管理者可以搜索规则、查看来源和最近评估、预览表达式、修改或复制规则、启停、删除及回滚。发行版升级统一提供新的内置基线，并保留本地修改和删除决定。部署者不需要为不同集群维护规则文件。

范围内包括数据源管理、GPU 能力发现、内置目录、规则管理、规则执行、告警生命周期、通知、权限审计、持久化及升级。范围外包括新增采集基础设施、训练模型、自动隔离/重启设备、完整多租户审批平台和默认高可用。底座具备的非 GPU 功能不作为本项目开发范围。

## 4. 功能需求与验收

| 编号 | 需求 | 验收标准 |
| --- | --- | --- |
| FR-01 | 只读接入 | 原 Prometheus 配置与规则保持不变，无写入接口或新增采集依赖 |
| FR-02 | 开箱初始化 | 空白数据库首次启动自动创建数据源、可编辑内置规则及通知绑定，无手工导入；重复启动无重复对象 |
| FR-03 | GPU 覆盖发现 | 按设备区分可用、不适用、元信息不足、指标缺失、陈旧、无效值、查询失败；显示每项原因 |
| FR-04 | 内置规则可信 | 每条规则具备出处、版本、适用硬件、输入、单位、表达式、时间语义、缺数策略及验证依据 |
| FR-05 | 新增与复制 | 新建/复制规则默认草稿，支持检查及预览；正式发布后才执行 |
| FR-06 | 查询与详情 | 按名称/ID、来源、严重度、启停、应用状态搜索过滤和分页，展示覆盖、最近评估和错误 |
| FR-07 | 修改与激活 | UI/API 在线修改；并发更新检查 revision；展示期望版本、实际版本和失败原因；失败保留原有效版本 |
| FR-08 | 启停与删除 | 支持启停和软删除；删除内置规则保留 tombstone；停止重复通知并保留历史及行政关闭原因 |
| FR-09 | 版本及恢复默认 | 不可变版本记录、差异查看、回滚为新版本；可恢复到指定内置目录默认值 |
| FR-10 | 升级保护 | 不覆盖自定义规则、本地改动、禁用及删除标记；冲突可见、可选择解决 |
| FR-11 | 权限与审计 | viewer 只读、operator 管理规则、admin 管理数据源/权限；记录操作者、时间、前后版本、结果，不记录明文密钥 |
| FR-12 | 设备级告警 | 稳定设备身份隔离；包含 cluster_id、device_key、rule_id/revision、观测值、依据及触发/恢复时间 |
| FR-13 | 通知能力 | 复用底座路由、分组、静默和重试；通知失败可见；明确重启及重投边界，不承诺恰好一次 |
| FR-14 | 持久化与恢复 | 规则、覆盖标记、版本和审计重启后保留；pending/firing 与重试行为有固定版本实测契约 |
| FR-15 | 运行可观察 | 健康、就绪、初始化/应用进度、覆盖、数据源错误、规则执行延迟和通知失败可查询 |
| FR-16 | 查询资源控制 | 数据源独立超时/并发/配额、窗口和返回序列限制；一条规则或一个源不能拖垮全系统 |

## 5. 规则数据与生命周期

规则至少包含稳定 rule_id、名称、builtin/custom 来源、目录版本、有效 revision、来源许可、适用条件、指标和单位、表达式、评估周期、持续/恢复条件、缺数及错误策略、严重度、通知路由、enabled、创建与修改人/时间。身份不依赖名称或易变的 pod 标签。

系统区分“发行版内置基线”“本地覆盖”和“实际生效规则”。用户修改产生覆盖，禁用也是持久用户决定。删除内置规则留下 tombstone，重启和升级不会复活。升级只自动更新未改基线；有本地改动时展示差异并保留当前有效版本。上游撤销规则时，未改对象退役，已改对象标记 upstream_removed 并提示复核。明确的安全撤销应单独通知，不能伪装普通更新。

表达式、持续条件或身份标签变化时，旧版本告警实例按 rule_changed 行政关闭，新版本重新按规定进入评估；禁用/删除分别记录 disabled/deleted，不能通知为“硬件恢复”。通知队列中的旧重复消息应取消或抑制，无法召回已发消息须写明边界。历史保留期限可配置。

每条规则独立发布并确认激活；没有底座证明时不承诺跨规则事务。若适用范围或元信息不足，规则可被保存但标为待条件满足，不伪造执行成功。

## 6. GPU 语义要求

稳定设备键采用 cluster_id + GPU UUID + 必要 MIG GI/CI 粒度。不能只用设备序号；替换设备和重建 MIG 不继承旧设备告警。空查询与单卡消失分别检测，维护曾发现设备的有限保留清单；不知道从未上报的设备数量时不承诺发现其缺失。

指标需按实际版本、名称、单位和 gauge/counter 类型核实。DCGM sentinel、NaN 和无穷值不得触发错误的硬件阈值；无效输入需另行呈现。XID 是错误码，不当作次数使用 increase。温度优先使用设备提供的阈值或经过硬件验证的配置，不给全部型号套用随意固定值。利用率或显存占用高低是容量/效率信号，不能默认等同硬件故障。

持续条件、窗口端点、计数器重置、数据陈旧和查询错误遵循所选底座明确语义，并用固定数据验证触发/恢复时间。没有原始信息的故障不承诺检测；监控覆盖不等于所有 GPU 故障覆盖。

## 7. 非功能要求与发布门禁

持久化配置与备份是交付的一部分。密钥使用 Secret/文件引用，认证只读最小权限，日志与审计脱敏。产品不执行任意用户脚本。规则预览也受资源限制。

规模指标在取得 GPU 数、时序数、采样周期、评估周期后制定；记录 CPU、内存、Prometheus QPS、评估延迟与通知延迟。不能虚构容量承诺。选型原型必须验证 pending 中途重启、firing 重启、通知断网、版本切换、删除告警及数据源中断；若底座恢复行为不满足约定，必须明确补偿能力或改选底座，不能静默降低要求。
