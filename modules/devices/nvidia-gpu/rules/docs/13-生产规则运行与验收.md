# 生产规则运行、变更与验收

**规范入口：**[第14篇GPU生产主清单](14-GPU监控指标与告警规则说明表.md)是本模块指标、规则语义、适用性及取舍的唯一规范基线。本文在主清单范围内解释需求、实现或操作；旧阶段结论不覆盖主清单。当前代码/台账/证据仅说明实际实现，不能因规范补齐而追认已上线；存在差异按主清单附录C登记。

版本：1.0.0-rc1；日期：2026-11-13。本文是生产安装和操作入口；[12-审计任务清单](12-生产就绪审计与任务清单.md)保留最初缺口，验收结论以运行服务 evidence 中的实际结果为准。真实 GPU 数据不是本次软件验收前提。

## 1. 支持范围

现有 Prometheus HTTP API、夜莺 9.3.0、DCGM 物理 GPU 指标契约 `dcgm-os-sre-physical-v1`。其他夜莺版本需先跑隔离兼容验收。37 个 DCGM 字段的版本和官方定位见 [provenance.md](../monitoring/os-sre/provenance.md)。不把全部工程窗口、持续时长或 PCIe 基线称为官方阈值。

配置默认 GPU 新鲜度 90 秒、计数窗口 300 秒、持续确认 60 秒；PCIe 持续确认至少 120 秒，并依赖明确的链路基线、传输指标和有效活动证据。部署者应按采样周期调整。隔离验收为了缩短时间采用 8/30/4 秒，PCIe 保持 120 秒。

无交换机/端口字段、无预期清单或无 PCIe 基线时，对应能力不可用。恢复 XID/SXid 必须提供绑定当前事件的运维确认，且随后采到有效的零码；人工操作不直接清除告警。计数器窗口退出只表示近期活动结束。DCGM 最后错误码不是完整硬件事件流，无法保证捕获两次采样间的所有事件。

## 2. 安装

在仓库根目录准备一个只归部署账号所有的私有配置目录，参照 [config.example.json](../runtime/config.example.json)创建 config.json。容器 UID/GID 为 1000:1000，挂载文件应允许该 UID 读取；凭据文件保持 0600，目录 0700。不要为解决容器权限而放宽令牌权限。

必填连接信息：Prometheus 地址及可选认证文件、夜莺地址、已有业务组 ID、已有通知规则 ID、夜莺可访问的网关地址。这里的夜莺业务组是告警配置容器，不是要求采集业务标签。确认通知策略实际绑定目标接收人和通道。网关仅提供有限告警查询接口，不承担通用 Prometheus 查询和历史图表。

配置 `profile.collector_job_regex` 限定 DCGM 采集范围。静态资产使用原 profile 的 gpus/switches/links/monitor_targets 格式，可参考 [profile.yaml](../monitoring/os-sre/profile.yaml)；编译时内联，不要求向已有 Prometheus 添加 recording rules。采集指标改名可在 `upstream.metric_aliases` 中配置逻辑字段到实际字段名；身份标签改名不在当前契约范围。

设置以下环境变量，路径均为部署机绝对路径：

```bash
export NPUMONITOR_RULES_CONFIG_DIR=/secure/npumonitor-rules
export NPUMONITOR_RULES_NETWORK=monitoring
export NPUMONITOR_N9E_TOKEN_FILE=/secure/credentials/nightingale-token
export NPUMONITOR_NOTIFY_TOKEN_FILE=/secure/credentials/watchdog-token
```

Compose 在解析时需要上述变量，包括可选 Watchdog 的凭据路径；未启用 Watchdog 时该文件不会挂载到运行服务。生产认证不由参考环境的 bootstrap 创建或修改。上游认证如需使用，可放在私有配置目录，配置 `upstream.auth_file` 为容器内 `/etc/npumonitor/upstream-auth.json`，内容为 bearer 或 basic 的 JSON 对象。

```bash
export PYTHONPATH=modules/devices/nvidia-gpu/rules/runtime/src
python -m npumonitor_rules.cli credentials --target "$NPUMONITOR_RULES_CONFIG_DIR"
python -m npumonitor_rules.cli compile --config "$NPUMONITOR_RULES_CONFIG_DIR/config.json" --output "$NPUMONITOR_RULES_CONFIG_DIR/bundle.json"
docker compose -f deploy/nvidia-gpu/rules/production/compose.yaml build sre-runtime
docker compose -f deploy/nvidia-gpu/rules/production/compose.yaml run --rm --no-deps sre-runtime python -m npumonitor_rules.cli init
docker compose -f deploy/nvidia-gpu/rules/production/compose.yaml up -d sre-runtime
docker compose -f deploy/nvidia-gpu/rules/production/compose.yaml run --rm sre-controller python -m npumonitor_rules.cli preflight
docker compose -f deploy/nvidia-gpu/rules/production/compose.yaml run --rm sre-controller python -m npumonitor_rules.cli sync-plan
docker compose -f deploy/nvidia-gpu/rules/production/compose.yaml run --rm sre-controller python -m npumonitor_rules.cli sync
```

初始化为显式操作；服务启动找不到数据库时拒绝启动，不把卷丢失当成全新健康状态。预检覆盖不完整时先处理缺口或禁用不适用规则，再执行同步。运行服务和夜莺之间采用 Basic monitor/viewer 凭据；管理操作采用独立 admin Bearer 凭据。跨不可信网络时配置网关 TLS 或由受控反向代理终止 TLS；上游和夜莺同样使用受控链路。

Watchdog 使用单独状态卷和独立 HTTP 通知出口：先 `run --rm sre-watchdog python -m npumonitor_rules.cli watchdog-init`，再 `--profile watchdog up -d sre-watchdog`。通知格式是 `npumonitor_watchdog` 事件 JSON，出口需支持该格式及 Bearer 认证。它不会经由正在失效的夜莺发送。

## 3. 日常检查与处置

`status` 展示最后轮询、错误及就绪状态；`preflight` 展示字段和逐规则适用性；`state` 展示 pending、active、unknown、事件及修订号。HTTP `/state` 用 limit/offset 分页，单页至多 1000 条。管理操作必须读取当前 revision，冲突后重新检查，不盲重试过期确认。

命令统一通过 controller 执行：`python -m npumonitor_rules.cli COMMAND`。

| 操作 | 命令或步骤 | 语义 |
|---|---|---|
| 恢复复核 | `recovery --rule RULE --identity '身份JSON' --expected-revision N --reason '复核依据'` | 当前 episode 专用、有有效期；等待有效零码，不能复用于新事件 |
| 设备退役 | `retire`，参数同上 | 管理关闭，审计记为退役，不声称修复硬件 |
| 重新纳管 | `unretire`，参数同上 | 解除退役记录，再按新输入评估 |
| 备份 | `backup` | 在线一致性 SQLite 备份，返回文件位置与摘要；凭据独立备份 |
| 恢复 | `restore --archive FILE --sha256 SHA --target EMPTY_DIR` | 校验摘要和数据库，只允许空目录；停服务后替换卷，保留原卷 |

采集缺失、无效、过期、乱序、重复及查询失败不会使已有硬件事件自动恢复。源样本时间不足也不累计确认时间；来源恢复后按有效样本继续。身份变化视为新设备，旧设备须显式退役，不能按机器上第几张卡合并。

## 4. 更新、同步与回滚

先备份。修改 config.json 并重新 compile 候选 bundle；运行中的生效版本来自数据库，不会仅因候选文件改变而自动生效。执行 `plan`，检查覆盖、签名及变化；使用 `activate --expected-generation N --reason '变更单说明'` 乐观并发控制，再执行 `sync-plan` 和 `sync` 更新夜莺。不兼容上游地址迁移须创建显式的新部署，不能悄悄改变原事件数据来源。

`releases` HTTP 接口查看历史摘要；`rollback --sha256 SHA --expected-generation N --reason '原因'` 恢复运行配置，再同步夜莺。`sync` 返回操作 ID，可用 `sync-rollback --operation ID` 补偿夜莺变更。存在外部修改则拒绝覆盖。停用规则是管理关闭，不能解释为恢复。

夜莺 API 没有在本项目验证过的跨对象事务或 CAS 保证。托管规则必须由该 controller 单写，避免人工编辑或并行同步；同步前检查漂移，正常请求失败进行补偿。进程在远端请求成功、回执持久化前崩溃属于不确定写入：保留 sync_operations 日志，使用 `sync-recover --operation ID` 核对远端操作标记与期望对象后补偿；与原状态相同则视为未写入，出现漂移则拒绝覆盖并交由人工核对。恢复命令已做故障单元测试；实际夜莺若规范化对象导致摘要不同，同样保守拒绝，不猜测写入结果。

凭据文件独立于 bundle；轮换需保持文件权限。viewer 令牌变更后用 `source-auth` 显式更新夜莺数据源认证。Watchdog 配置绑定存储摘要，变更目标/出口需单独安排迁移，不能删除旧 outbox 重建以丢弃待发消息。

## 5. 验收与交付边界

[运行服务说明](../runtime/README.md)给出可复现测试入口；[evidence](../runtime/evidence)记录实际结果，不以未来计划代替已通过证据。53 项 PromQL 用例与运行服务测试、真实软件模拟链路互补。

单实例 SQLite WAL、独立通知 outbox 和显式备份恢复是当前设计。HA、多副本、跨地域、完整硬件事件采集、NPU 都不属于此版本承诺。不能将一次 100 张模拟 GPU 的短时测试外推为任意规模或长稳通过。发行前还需固定 Git 提交和镜像 digest，将所有 P0 项的未验收条目完成后再将 RC 作为生产正式版发布。

## 6. 本轮实际测量与已知缺口

隔离模拟源 100 张 GPU、2 秒抓取/轮询、8 个查询 worker、30 秒窗口；PCIe/Fabric/预期链路清单配置了其中 2 张卡，其余卡仅测试不依赖清单的检测。约 30 秒采样期间，查询与元数据请求合计约 22.61 次/秒，单轮最长约 1.37 秒；Docker 一次快照为 CPU 72.60%、内存 156.2 MiB。该参考容器未施加生产 Compose 的 1 CPU/512 MiB 限额。结果不能替代受限资源下的长稳、多节点或全部100卡清单规则容量验收。

实际将本地 HTTP 通知接收端设为 503 后，夜莺原生通知策略没有暴露预期的 `n9e_alert_alert_notify_error_total`。失败记录见 `notification-counter-negative.json`，后续能力缺口检查见 `operations.json`。参考配置及生产示例均保持 `notification_counter_verified=false`；只有在实际使用的发送路径验证过计数覆盖后才能显式启用。独立 Watchdog 的通知重试已验证，这不等价于覆盖所有夜莺通知通道的失败。

CI 配置已加入仓库，执行来源/生成物/布局、配置、运行服务和 PromQL 测试；本轮为本地执行通过，尚未将工作区推送并验证 GitHub Actions。真实软件的完整隔离故障演练仍按 README 命令顺序执行，不将它们标为远端CI已经运行。
