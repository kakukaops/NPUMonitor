# 逐项核查 H100 指标与规则覆盖

核查日期：2026-11-06；范围：H100物理卡，PCIe/SXM/NVL配置待确认，MIG实例级尚未准入。

**当前不全面。** 仓库正式目录只有 **1个指标、1条草案规则，已发布/默认自动启用规则为0，真实H100验证为0**。已有六条模拟规则证明了部分采集、判断和通知链路；18组样本、31个断言只验证一个新ECC表达式，不能换算成H100故障覆盖率。本次已完成仓库清点、官方故障域对照、重点字段及XID适用性核查，并整理出待补清单；尚未完成固定版本全字段登记和现场输入核验。要证明全面性，必须对明确配置和版本下的每个检测目标给出处置与分层证据；不能承诺所有未知硬件故障都能被指标规则发现。

## 1. 现有成果是局部样例，型号适用性仍未验证

正式的[指标目录](../../common/monitoring/catalog/metrics.yaml)和[规则目录](../monitoring/catalog/rules.yaml)仅登记volatile不可纠正ECC计数及其近期新增判断，均为draft，规则默认disabled。[硬件目录](../../common/monitoring/catalog/hardware.yaml)中的三种H100形态均未完成字段采集和现场验证，型号准入也未实现。产品支持H100、DCGM定义某字段、Exporter配置该字段、现场实际持续提供有效样本，是四个不同层次。

[六条实验规则](../rules/lab-catalog.json)涵盖温度示范、XID79、DBE新增、采集失败、设备温度序列消失及NaN温度，明确限制在模拟集群。它们的[链路验收](../docs/07-首批模拟规则验收报告.md)不能替代新ECC草案的夜莺验收，更不能替代H100兼容验证。[18组/31断言](../monitoring/tests/README.md)也不执行夜莺状态机或真实硬件采集。

NVIDIA说明Exporter按配置选择字段，配置类型不自动证明语义正确，配置存在也不保证运行时发出字段。因此不能仅凭“已安装DCGM+Prometheus”认定输入齐全。([Exporter指标与运行限制](https://docs.nvidia.com/datacenter/dcgm/latest/reference/dcgm-exporter-metrics.html))

## 2. 内存、互联及监控自身健康都有明确缺口

下表是与官方资料对照后的工程审查结论，列出的字段都是**候选输入，不是已验证H100支持清单**。版本映射、实体粒度和现场可见性仍需逐项核实。

| 检测域 | 应核对的输入和语义 | 当前正式覆盖与主要缺口 |
| --- | --- | --- |
| ECC与内存可靠性 | DRAM/SRAM、纠正/不可纠正、volatile/aggregate；SRAM超阈值标志346 | 仅汇总volatile DBE草案；统计细分、SRAM状态和H100适用性未补齐 |
| 行重映射 | failed395、pending396、总数393/394、资源桶385–389 | 无正式指标/规则卡；模拟器输出failure字段也不等于已有对应规则 |
| XID与错误影响 | H100适用码、严重度、contained/uncontained、恢复动作 | 正式目录无规则；实验只演示79码，未覆盖H100目录或事件关联 |
| 温度与降频 | GPU/HBM温度、设备门槛/余量、热限制时长、时钟原因 | 无正式卡；85°C只是实验值，不能成为H100统一阈值 |
| 功率与时钟 | 配置/有效功率限制、外部power brake、限制原因 | 无正式卡；TDP、高功耗或低频本身不能直接等同硬件故障 |
| PCIe | replay、链路速率/宽度及负载上下文 | 无正式卡；低吞吐不能单独证明链路故障 |
| NVLink/NVSwitch/fabric | Hopper专用错误字段、预期端口/对端、switch及Fabric Manager | 无正式卡；形态和拓扑未知，GPU遥测不能证明交换机受监控 |
| 监控与管理组件 | 设备/字段发现、缺数、陈旧、特殊值、InfoROM/驱动、查询/通知失败 | 只有局部实验和ECC guard；缺少正式数据质量及链路自监控规则 |
| 容量与效率 | 显存、算力/带宽负载及作业分配上下文 | 无正式策略；应以看板或可选业务策略处理，不能凑成硬件告警 |

内存字段和行重映射状态有不同含义；官方SRAM判据涉及bank级unique UCE和Field Diagnostic，不能把这些条件套到汇总DBE总计数。([DCGM字段目录](https://docs.nvidia.com/datacenter/dcgm/latest/dcgm-api/dcgm-api-field-ids.html)、[内存可见统计](https://docs.nvidia.com/deploy/a100-gpu-mem-error-mgmt/latest/user-visible-statistics.html)、[SRAM判据](https://docs.nvidia.com/deploy/a100-gpu-mem-error-mgmt/latest/sram-uncorrectable-errors.html))

本次枚举官方XID目录HTML表：**172个代码行中78行明确标为H100适用**，其中包含信息性和IGNORE项，不能解释为应新增78条呼叫告警。该页面于2026-11-04更新，本次2026-11-06核查的是滚动快照，摘要及代码ID保存在[枚举记录](<../research_notes/H100 指标 规则 覆盖审查/h100_xid_enumeration.json>)，页面SHA256为`ee085d5e99de9f4524ac6233f787eb59ddc382b55bfbcb29a49dd34982d82be2`。78项均需分类留痕；本次目录中XID160对H100为NO，不能直接从通用内存页面移入H100规则。([官方XID Catalog](https://docs.nvidia.com/deploy/xid-errors/latest/analyzing-xid-catalog.html))

版本差异同样影响覆盖：固定Exporter配置给Hopper分组的NVLink CRC/recovery/replay字段是497/498/499，且在该配置中被注释；旧架构及NVLink5+字段不能直接继承。行重映射等字段的新旧宏名也有差异，必须建立字段ID→目标版本宏名→Exporter实际名称的映射。([固定Exporter配置](https://github.com/NVIDIA/dcgm-exporter/blob/fafd151148052628061a80450b4ee037a5fa0c3c/etc/default-counters.csv)、[固定DCGM字段源码](https://github.com/NVIDIA/DCGM/blob/9fae2867e6e5264fa0fca22a07dc898d591baa21/dcgmlib/dcgm_fields.h))

温度需设备门槛和限制原因，互联需预期拓扑；NVSwitch是独立实体，不应对未使用端口或不支持的状态统一报故障。([温度/时钟定义](https://docs.nvidia.com/deploy/nvidia-smi/index.html)、[拓扑与链路](https://docs.nvidia.com/datacenter/dcgm/latest/learn/core-services/topology-and-links.html)、[NVSwitch监控](https://docs.nvidia.com/datacenter/dcgm/latest/learn/modules/nvswitch.html))

## 3. 全面性要由双向登记和证据链证明

**先冻结现场边界。** 记录H100形态、GPU/UUID、MIG状态、NVLink/NVSwitch拓扑、驱动/DCGM/Exporter及采集文件版本、刷新和scrape周期。现在这些资料缺失，不能确认某项目“不适用”，也不能选择一个形态作为全H100的代表。

**再冻结两份可枚举登记册。** 字段登记册从固定DCGM字段、健康系统、Exporter清单逐项分类为告警输入、看板、上下文、有据不适用、输入缺失或待核实。检测目标登记册从官方故障域、内存状态、H100适用XID、排障及驱动已知问题反向查输入。每项都有来源、结论、理由和负责人；别名不重复计数，未采集不冒充不适用。附录24项是启动审查的提案，**不是官方完整规则包，也尚不能作为覆盖百分比的分母**。官方被动健康检查所涵盖的子系统可作为查漏入口，但Healthy只反映已启用检查在保留数据中未发现事件，不等于全系统受监控或主动诊断通过。([DCGM健康监测](https://docs.nvidia.com/datacenter/dcgm/latest/learn/modules/health-monitoring.html)、[固定3.1健康系统枚举](https://docs.nvidia.com/datacenter/dcgm/3.1/dcgm-api/dcgm-api-structs.html))

**用实际输入闭合每条链。** 每个目标须关联“官方依据→H100配置→有效字段→规则→边界用例→夜莺→通知→处置”。核对原始`/metrics`的HELP/TYPE/标签，再与Prometheus metadata、targets、series和逐设备查询对照；检查重复采集、缺数、sentinel、重置及身份变化。`up=1`只证明该scrape成功，不证明每张卡、每个必需字段完整。([Exporter运行限制](https://docs.nvidia.com/datacenter/dcgm/latest/reference/dcgm-exporter-metrics.html#runtime-considerations)、[Prometheus抓取目标](https://prometheus.io/docs/concepts/jobs_instances/))

无效输入被硬件表达式过滤后，还须有数据质量/覆盖提示，否则无告警仍会被误读为健康。缺少日志事件顺序、恢复动作、switch实体或诊断结果时，保留为能力缺口；不能在本项目“只读已有Prometheus”的约束外悄悄增加采集，也不能删除缺输入目标后宣称完整。

## 4. 第一版应分别验收各阶段，保留未知项

| 度量 | 可审计的分母与分子 | 当前可报告的结果 |
| --- | --- | --- |
| 来源处置完整性 | 冻结来源全部字段/判据中，有分类和理由的项 | 尚未完成全量登记，不给百分比 |
| 型号适用性 | 全部配置—目标项中，有证据判适用或不适用的项 | H100三形态仍有unknown；未知保留在分母 |
| 现场可观察性 | 已确认适用目标中，逐设备有效/新鲜输入齐全的项 | 无真实H100样本；另列未知及输入缺口数量 |
| 告警实现 | 已审定需告警目标中，有审阅通过规则的项 | 仅1条draft，不能算已发布覆盖 |
| 分层验证 | 已批准目标/规则用例中，表达式、夜莺、真实H100分别通过的项 | 单表达式18组/31断言；新草案夜莺与真实H100未运行 |

第一版应先补型号/输入与数据质量，再补严重内存状态、XID、温度降频及按实际拓扑适用的互联；容量效率单列可选策略。高优先级目标须有卡片、输入和处置证据，缺输入或不支持的部分明确交付，不得被大量看板指标稀释。发布只能声明已确认配置和观测边界内的覆盖，不能将文档处置完整率当作故障检测率。

后续通过固定来源diff捕获新/删/改字段、类型、单位、实体支持与错误定义，产生待审任务；规则、参数或适用范围变化时重新回归并生成覆盖差异报告。现场故障复盘继续补充漏检目标。在线遥测没有可辨识信号、采样间隙中的事件、依赖日志/作业上下文或主动诊断的问题，始终需要单独说明边界；官方也将被动监控与主动诊断区分。([DCGM健康监测](https://docs.nvidia.com/datacenter/dcgm/latest/learn/modules/health-monitoring.html)、[GPU排障流程](https://docs.nvidia.com/deploy/gpu-debug-guidelines/gpu-node-triage.html))
