历史冻结草案；当前现场规则见[OS SRE版本](../os-sre/README.md)。

default_policy：disabled；维护者：GPU监控规则库维护者  
结构化定义：[rules.yaml](../catalog/rules.yaml)；输入：[指标说明卡](../../../common/monitoring/metrics/nvidia.ecc_dbe_volatile_total.md)

## 1. 检测目标与影响

目标是在有效数据中识别某张物理卡的volatile不可纠正ECC计数近期增加，并通知值班人员核查设备及作业影响。它不负责确认永久硬件损坏、自动修复、自动隔离或精确还原每次错误的发生时刻。

覆盖目标：nvidia.ecc_dbe_increment。单设备以cluster_id+UUID定位；观测窗口内的变化不是终身累计量。

## 2. 判断依据与适用条件

- 官方事实：DCGM提供该类总计数字段；引用Exporter配置将其声明为counter；NVML说明volatile重置行为。来源：nvidia.dcgm.fields / nvidia.exporter.counters / nvidia.nvml.ecc。
- 官方执行语义：Prometheus increase按counter下降处理重置并对窗口进行外推，所以结果可能不是整数；不能把观测值直接写成“准确发生N次”。来源：[prometheus.functions，固定v3.2.1](https://github.com/prometheus/prometheus/blob/v3.2.1/docs/querying/functions.md)。
- 工程判断：正增量值得调查；critical级别、5分钟窗口、30秒评估和90秒新鲜度均是本项目提案，尚待现场审定，不能表述为官方推荐阈值。

部署前需确认ECC支持且启用、字段有效且确实采集、单物理卡序列映射明确、cluster_id和UUID稳定。MIG、型号/版本白名单、重复采集策略未验证，均不能默认准入。新表达式不修改Prometheus rule_files，也尚未导入夜莺。

## 3. 完整表达式及解释

以下与YAML一致，使用原始字段，不依赖尚未存在的“清洗指标”：

```promql
(increase(DCGM_FI_DEV_ECC_DBE_VOL_TOTAL{cluster_id!="",UUID!=""}[5m]) > 0)
and (min_over_time(DCGM_FI_DEV_ECC_DBE_VOL_TOTAL{cluster_id!="",UUID!=""}[5m]) >= 0)
and (max_over_time(DCGM_FI_DEV_ECC_DBE_VOL_TOTAL{cluster_id!="",UUID!=""}[5m]) < 9223372036854775792)
and (sum_over_time(DCGM_FI_DEV_ECC_DBE_VOL_TOTAL{cluster_id!="",UUID!=""}[5m]) >= 0)
and (count_over_time(DCGM_FI_DEV_ECC_DBE_VOL_TOTAL{cluster_id!="",UUID!=""}[5m]) >= 2)
and ((time() - timestamp(DCGM_FI_DEV_ECC_DBE_VOL_TOTAL{cluster_id!="",UUID!=""})) <= 90)
```

第一段保留近期正增量。后续分别检查窗口内负值、INT64无效区间/正无穷、NaN污染、至少两个样本以及当前样本新鲜度；负无穷同样被最小值检查排除。sum检查的NaN行为必须用固定样本验证，不能只凭阅读表达式认定正确。

有效性检查作用于整个窗口，避免只检查当前值时，将“无效值→正常值”的过程误当巨大的counter变化。保留原有标签，不跨设备求和。cluster_id和UUID为空的序列不进入规则，但还需要覆盖检查报告这个缺口。

这组guard只阻止无效/不新鲜数据进入硬件判断，不会自动创建数据质量告警；不能用空结果宣布健康。它也不能证明窗口内没有采样间隙。只允许现场没有超前时间戳的数据，时间同步异常需单独处理。

## 4. 参数与默认值

| 参数 | 样例值 | 依据 | 可调性与影响 |
| --- | --- | --- | --- |
| 增量阈值 | >0 errors | 正增量语义，不是人为选择容忍N次 | 改阈值会改变检测目标，需重新审阅 |
| 窗口 | 300秒 | 工程提案，平衡留存与重复提示 | 可调，修改[5m]、用例和版本 |
| 评估周期 | 30秒 | 工程提案 | 可调，需匹配scrape及查询预算 |
| 持续时间 | 0秒 | 工程提案，不额外延迟已观测错误 | 可调，过长可能漏掉短窗口事件 |
| 当前样本最大年龄 | 90秒 | 基于30秒scrape的工程提案 | 可调，需同步表达式及缺数策略 |
| 最少样本数 | 2 | 差分计算最低要求，不代表覆盖完整 | 只能在重新验证后调整 |
| INT64无效下界 | 9223372036854775792 | 固定DCGM源码定义 | 语义常量，不作为用户业务阈值 |

首次评估不一定在错误发生时刻。新卡只上报一个非零样本、采样之间发生错误又重置、数据间隙后的外推均可能影响结果。不能承诺恰好一次或精确事件计数。

## 5. 触发、结束与异常输入

| 情况 | 规则含义 | 告警/覆盖要求 |
| --- | --- | --- |
| 有效窗口存在正增量 | 近期观测到新增错误 | 进入critical候选告警，无额外for等待；夜莺新版本尚需实测 |
| 有效窗口不再有正增量 | 近期新增条件退出 | 结束文案不得写成“GPU硬件已修复” |
| 缺数/陈旧/无效值 | 判断依据不足 | guard可能使表达式为空；覆盖须标indeterminate，不能认定健康 |
| 查询失败 | 未完成本轮评估 | 需平台错误可见；重启/错误状态不保证等价恢复 |
| 计数器重置 | 按counter语义处理 | 单纯清零不当作新错误；重置前后的真实新增仍可能触发 |
| 禁用、删除或规则变更 | 行政结束或重新评估 | 与硬件恢复分开记录 |

夜莺原生可能把表达式无结果当作恢复，单条PromQL不能区分所有结束原因。配套数据质量规则和结束文案/状态展示尚未准入，这是发布阻塞项；样例的期望策略不等于底座已经实现。

## 6. 严重度、通知与处置

严重度提案：critical，对应夜莺1。依据是不可纠正错误的潜在风险，不代表每次都已造成作业失败；需结合业务分级审定。

触发文案：`GPU近期观测到不可纠正ECC计数新增，请核查设备和作业影响`。

结束文案：`近期新增条件已退出，请核对数据质量；不代表硬件已修复`。

通知至少携带rule_id/version、cluster_id、UUID、观测增量、窗口、事件时间、数据质量与结束原因；不把外推增量当作精确错误次数。

处置步骤：

1. GPU平台值班人员先核对UUID/型号、采集源和样本新鲜度，确认不是重复采集或无效字段。
2. 查看同设备计数趋势，核对驱动加载/清零/节点变更时间；保留原始指标和时间线。
3. 关联XID、其他内存可靠性信息与作业错误，区分硬件、驱动和应用线索。没有这些输入时明确记录无法进一步判断。
4. 若持续新增或业务受影响，按现场GPU故障流程升级给硬件/平台负责人；诊断、隔离、重置、重启及更换由授权人员评估执行。本规则不自动执行这些动作。
5. 结束前同时核对数据质量和业务影响，窗口退出本身不作为维修完成证据。

## 7. 误报、漏报与关联规则

重复采集、标签重建和MIG重复暴露可能形成多个实例或改变counter基线；必须在准入时解决。首次发现即非零不能证明最近新增；跨采样间隔的错误和重置可能完全不可见。窗口过滤无效值后，可能暂时无法判断真实错误，必须配套数据质量提示。

关联方向：ECC输入无效/陈旧、设备/采集缺数、XID及其他内存可靠性信号。这些依赖仍待建立正式规则卡；当前没有声称已提供完整抑制或根因归并。
